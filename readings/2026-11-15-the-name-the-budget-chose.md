## §4 §3.3 の配線：compared_touch_count を不確実性へ

### §4.1 前提の訂正：compared の名指しは、すでに不確実性に入っていた——ただし名前無しで、満額で

前報告 §3.3 はこう書いた——「`compared_touches` は宣言され加算されるだけで、リポジトリ全体に他の使用箇所が無かった。各仮説の `compared_touch_count` として信念状態に載せた。**式には入れていない**：`uncertainty` に繋ぐと事後確率が動き、台帳の過去の行の意味が変わる」（§10-2 も同じ保留理由を繰り返す）。これは**コードの経路については誤りだった**。別の経路で比較の名指しはすでに式に入っていた。

```python
for cid in compared:
    compared_touches[cid] += 1
    indep_sources[cid].add(f"cmp:{ev_type}:{source_key}")   # ← これ
```

`indep_sources` は不確実性の分母 `sqrt(1 + n_indep)` の `n_indep` を作る。つまり**比較欄に書かれた仮説は、出所が別なら1件ごとに「独立ソース1件分」の割引を受けていた**（重複は source_key で畳まれる）。`compared_touch_count` という数自体は誰も読んでいなかったが、比較という行為の情報量は満額（1.0）で不確実性に入っていたのである。

委任は「繋いでください（過去の評価の意味が変化しても良い）」だった。繋ぎ方には二つの選択があった。

- (α) 既存の `cmp:` 経路をそのまま残し、`compared_touch_count` を追加の項としてさらに足す。→ 同じ比較を二度割引く（二重計上）。
- (β) `cmp:` 経路を外し、比較を**明示的で減衰した形**で `compared_touch_count` 経由に配り直す。→ 比較の重みをこの機会に設計できる。

(β) を選んだ。理由：(α) は「比較は独立ソースと同価」という暗黙の設計を強化するだけで、その設計自体に検証が無い。一方、（直接評価は対象への証拠だが）**比較は仮説を「名指した」だけで「検査した」わけではない**——この向きは前ラウンド §12.11 が測ったとおり「名指した側の効果は比較の有無で target の δ が 1.538 倍になる」が、名指された側について証拠が届くわけではない。よって比較は独立ソースより弱く扱うのが筋である。

### §4.2 入れた式


### §7.4 (9) Q-002 の同着は消えた。機構（厳密不等号）は残っている

**現行計数（HEAD=e5d71e0 で再測定）：** Q-002 の active 7件から作る21ペアで、EIG が厳密に0.0000 のペアは **15本**（事後確率が0の3仮説——`HYP-20261112-16929d` P=0.0000、`HYP-20261112-afd1a5` P=0.0000、`HYP-20261112-ba8bff` P=0.0000——を含む全ペア）。最大値は一意である：`HYP-20261113-977052`（P=0.6322） vs `HYP-20261115-8f6552`（P=0.2682）、EIG=0.1237（次点 0.0211、約6倍差）。**トップは同着ではない。**

**判定：** 直すなら (i) EIG=0 のときは対を推薦しない、(ii) 同着を明示して複数提示する、のどちらかだが、どちらも推薦パケットの中身を変えるので editorial_review のものである（委任により本ラウンドは機構を変えない、という裁定は §5.3 と同じである）。**本ラウンドは機構を変更せず、現状（一意トップ・15本の0.0000ペア・厳密不等号）を記録するに留める。** §5.1 の「評価0件を含むペアを優先しない」規則は EIG=0 の同着には作用しない（例えば0.0000ペアの中に両側評価ありのものがあっても、トップが一意な限り意味が無い）。

### §7.5 (10) 新ゲートは「本文が存在する」までしか言わない——置き換え検知に何が要るか

**現在のゲートが言うこと／言わないこと（`tools/readings_integrity_check.py`）：**

| 検査 | 捕まえるもの | 捕まえないもの |
|---|---|---|
| `blank_body` | 0バイト／空白のみの .md | 本文の書き換え |
| `no_h1` | `# ` 見出しの消失 | 見出しがあるままの別本文 |
| `missing_target` | 指されたファイルの欠損 | 中身の差し替え |

**置き換え（本文が別の本文にすり替わった）を捕まえるには、バイト保存の層が要る。** それは `append_only_check.py` が state/ 行でやっていることである：基準点（`origin/main` 等）に存在する行が、バイト単位で同一に残ることを見る。`readings/` で同じことをやると何が壊れるか。

1. **正当な改訂（節の追記・訂正）が全て違反になる。** 本文の規則は追記専用ではない。先例として本報告自身の改訂・前報告 §11 の追記が壊れる。
2. **スキーマが要る。** バイト保存を正当な変更で通すには「この本文は意図的に更新した」という記録（どの行が新しい本文を正当化したか）を台帳に持たせる必要がある。例えば `notes` 行に `content_sha256` を持たせ、本文を編集したセッションは新ハッシュを書く——という**本文版台帳**の層を `state/` に1枚増やす設計である。
3. **初期配備の断絶。** 現行818本の .md をいつのハッシュで固定するか（凍結時点をコミットに記録し、そこ以降の不一致を全て違反と読ませるか）。凍結点より前の改訂は正当として通し、凍結点以降は台帳の行を要する、という移行が可能だが、これは新しい追記規則とゲートの新設であり、本ラウンドの委任（6件）に無い。
4. **偽陰性は残る。** 「台帳に行を書いた上で本文だけ差し替える」攻撃は捕まる（ハッシュが合わない）が、「行ごと意図的に整合させて差し替える」正当に見える改訂は、そもそも台帳の信頼を前提とするので、検査の対象外である。**検査は『台帳と本文の整合を強制する』以上のものではない。**

**したがって「書庫の本文は検査面で守られている」と言うとき、正確にはこう言えるだけである：**

> 本文は「在ること」「空でも見出し無しでもないこと」「ノートから指された先が在ること」については検査面で守られている。**本文が同一であること**はどの検査も主張せず、それを実現する層（本文版台帳＋ハッシュ照合ゲート）は未実装である。検知したいなら、(a) 上記の本文版台帳を新設して追記専用の層を `readings/` にも持ち込むか、(b) git 側の保護（`readings/` への push を ruleset で制限する等、リポジトリの外の層）で済ませるか、のどちらかが要る。(a) は正当な改訂のコストを上げ、(b) は人間の判断を経ない変更を減らすが書庫内の手段ではない。**どちらも editorial_review／人間の決断のものであり、この委任の範囲ではない。**

今回作らなかったのは、正当な改訂を壊す門を「見かけの完全性」のために作るべきではないからである（報告自身の §2.4 が同じ理由で追記専用を `state/` に限定したのと同じ裁定）。
