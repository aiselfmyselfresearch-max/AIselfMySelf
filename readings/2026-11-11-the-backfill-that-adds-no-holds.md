## §0 質問への答え——保留は増えない。前回の一文が誤っていた

利用者の問い：「古びた保留が増えても問題ないのか」。

**答え：この登録では1件も増えない。** 前報 §4 に「359本が台帳に入れば古びた保留もその分だけ増えます」と書いたが、**それは (b) claims を付ける場合の話で、(a) 機械行には当てはまらない。** 私の一文は、二つの段階を混ぜていた。

理由は単純である。**保留は `claims` の中にしか存在しない。** `tools/note_index.py --register` が書く欄は次の8つだけで、`claims` は無い。

```
note_id / path / session_id / created_at / mode / date_real / report_session_id / read_depth
```

**359行を書いた直後に数えた：claims を持つ行 0、`reading_held` 0件。**

## §3 残る危険と、その扱い

登録した359本の本文には、**「保留」の見出しを持つものが137本**、語として「保留」を含むものが**234本**ある。これらは claims ではないので `held_report.py` には現れないが、**到達可能になった**——`read_log` から引け、`note_index --for-id` で見つかる。

| 危険 | 実測 | 扱い |
|---|---|---|
| 台帳上の保留が増える | **0件**（claims が無い） | 増えない |
| 本文の「保留」節が現在形として読まれる | 137本 | `read_depth` が未読を明示。claims が無いので `held_report.py` の集計にも入らない |
| 未読の報告が「読んだ」ことにされる | 359行すべて `metadata_and_structure_only` | スキーマの欄で明示 |

**つまり、危険は「数が増える」形ではなく「読めば見える」形で残る。** 前者は0、後者は137本。そして後者は今日の誤りとは別種である——今日の誤りは、**claims に書かれた保留**が閉じなかったことから出た。

## §4 予算の引き上げ（と、その言い訳をしないこと）

| 項目 | 前 | 後 |
|---|---:|---:|
| `state/notes.d/` | 1,012,429 B / 92ファイル | **1,117,925 B / 94ファイル** |
| soft（bytes） | 1 MiB | **1.25 MiB** |
| soft（shards） | 92 | **96** |
| hard | 4 MiB / 160 | 変更なし |

`tools/size_budget.py` の同じ表には、**1日で 80→88 まで上げた履歴と、それに対する自己批判**が注記として残っている（「もはや "narrow exception" の防御可能な読み方ではない」）。今回の引き上げはその型と違う、と**言い切るつもりはない**。違う点は二つだけである。

1. **一度きりの索引 backfill**であって、セッションごとの +1 ではない。行数が報告数（690）に追いついたので、**今後この箱が伸びるのは claims によるべき**で、行によるべきではない。
2. 増えた行は**判断を含まない**ので、統合（consolidation）で回収する対象が無い。回収できるのは行そのものを消すことだけで、それは追記専用に反する。

**正直に書けば、これは「狭い例外」ではなく「台帳の形を整える工事」である。** 工事は一度で終わるが、終わったことを記録しないと、次の回はまた +1 を積む。

## §5 判定（形式・外延・意味の自己申告）

- **形式**：§1 の欄の内訳は新シャード2本の実測、§2 は `validate_seed`・`note_index --report`・`held_report.py`・`wc -l`。
- **外延**：「保留は増えない」は**台帳の claims について**の主張である。本文の「保留」節が現在形として読まれる危険は消えていない（137本）。**そこまで含めて「問題ない」とは言っていない。**
- **意味**：359本の中身は読んでいない。**読んでいないことを、`read_depth` に書いた。** 主張の真偽は判定していない。

## §6 限界

1. **359本の claims は空のままである。** 「登録された」は「読まれた」ではない。
2. **`mode` は243/359、`date_real` は181/359 しか埋まっていない。** どちらも導出値で、ファイルから取れないものは空にした（推定で埋めていない）。

4. **予算の引き上げ幅は、測定ではなく工事の都合で決めた**（1.25 MiB は実測 1,117,925 B に 17% の余裕）。次の回に測り直すべき値である。
