## §2 計器が自分の文書に書いた検査を走らせていなかった

### §2.1 欠落

`HYP-20261113-17ea95` の scope_conditions 第二項は原文でこうである。

> 検査（**validate_seed.py・append_only_check.py・belief_state.py --check-map**）が判断内容の整合性のみを対象にしている運用

三つ名指しされている。反証条件 (b) は「経路の損耗が**判断内容の検査で**検出できる（検査が経路の状態を読み取っている）と示される」であり、この三検査が (b) の採点対象である。計器の docstring もその三つを列挙し、「他の検査で採点するのは仮説がしていない主張を検査することになる」と正しく注意していた。

しかし 2026-11-15 以前の `probe.CHECKS` は六件で、`named_in_scope` の印が付いていたのは二件だけだった。

```
probe named_in_scope : ['validate_seed', 'belief_state_map']
hypothesis names     : validate_seed.py, append_only_check.py, belief_state.py --check-map
MISSING              : append_only_check
```

`grep -c append_only_check tools/execution_path_probe.py` は **1** を返す。その一行は docstring の中の言及である。計器は、**自分の説明文が名指しした検査を実行していなかった**。

これは前ラウンドの `tools/preservation_layers.py` の欠陥と同じ型である。あちらは ID 認識子が17系のうち6系しか認識せず、反証できる側だけを小さく報告していた。今回は名指し集合の3分の2しか検査していない。どちらも**誤りが片方向**で、どちらも**反証の可能性を減らす向き**である。道具が違うだけで、作り方の癖が同じだった。

### §2.2 追加したら、そもそも走らなかった

CHECKS に `("append_only_check", ("tools/append_only_check.py",), "named_in_scope")` を追加して走らせると、baseline が all-green でなくなった。計器自身が「WARNING: baseline is not all-green; flips below are confounded.」と正しく警告した。

原因を分離した。サンドボックス内で直接実行すると exit 2、出力は次のとおりである。

```
CANNOT COMPARE: commit 'HEAD' is not available in this checkout
  A shallow checkout needs the commit fetched first (CI: actions/checkout with fetch-depth: 2).
```

`append_only_check.py` は `git archive <rev> state` で台帳を過去のリビジョンと比較する。`make_sandbox` は COPY_DIRS（state, tools, schema, docs, prompts, readings, taxonomy）だけをコピーし、`.git` をコピーしない。だから比較相手が存在しない。

これは**検出ではない。実行不能である。** そして実行不能は、合格として数えられていた。六検査の時代には `append_only_check` が走らないこと自体が観測されなかったので、この区別は誰にも見えなかった。

### §2.3 直し方

`.git` をコピーするのは誤りである。外側のリポジトリの HEAD はセッション中に未コミットの作業を抱えるので、baseline が「無介入のコピー」ではなくなり、I0_control 自体が差分を出して全ての反転が解釈不能になる。

代わりに、**サンドボックスの中で pristine な state/ を一回コミットしてから介入を適用する** `commit_baseline(sb)` を追加した。これなら比較はまさに実験が望むもの——介入 対 無傷——になり、外側リポジトリのコミット状態に依存しない。コストは1サンドボックスあたり約1秒である。

`baseline_committed` を各介入の記録に追加し、git が無くてコミットできなかった場合は render が明示的に警告するようにした。「反転なし」が「走らなかった」に化ける経路を塞ぐためである。

### §2.4 結果

修正後の baseline は七検査すべて exit 0、all-green。そして：

```
PASS: all 28145 ledger lines of HEAD (origin/main is not available here)
      are still present byte for byte
```

`append_only_check` は I1（シャード分割）・I2（接尾辞改名）・I3（日付偽造）・I4（上限引下げ）の**四つすべてで PASS** した。理由はこの検査が**行の多重集合**を比較するためである。シャードを分割しても接尾辞を改名しても、行は1バイトも変わらない。ファイル名は比較対象ではない。

つまり limb (b) は、名指し三検査すべて・十一介入すべてに対して**発火しない**。前ラウンドまでの「二検査に対する不発」より強い主張が、初めて測れた。不発は本物である。ただしそれは、この検査が物理的配置を読む検査ではないからであって、経路の損耗が存在しないからではない——I3 の日付偽造は `date_axis_shards` と `learning_metrics` を実際に反転させており、検出器が壊れていないことは陽性対照として既に立っている。

## §3 釘付けにされていたパラメータ

### §3.1 シードは経路である

`tools/inspect_inquiry.py` は `--seed` を取る。そしてそのシードは、`assign_session_role`（`:975`）で**探求ロールを決め**、参考モードを決め、§0.5 の候補窓——衝突させるモチーフの組、左右の素材候補、衝突候補の先行断片、改稿・変奏候補の草稿、正面応答候補の深い open 問い——の**中身を決める**。台帳の行は一行も読まないし、書かない。

これは定義どおり実行経路である。判断内容を変えずに、次の読み手の行為だけを変える。`17ea95` の scope_conditions 第三項「経路の変化が、判断内容を書き換えずに後続の読み手の行動を変えうる系」がそのまま当てはまる。

ところが `run_packet` は `--seed 17ea95` を直書きしていた。コメントは「auto 選出の派生問いは仮説が無かったり素材が足りなかったりして、並び・予算のツマミを効かせられない」と説明していた。**その説明は正しい。そしてそれは、ツマミを効かせるためにシードを固定した、ということを意味していた。** 四つのパケット介入は全部、一つのシードの下でのみ測られていた。

### §3.5 動かなかったもの

同じくらい重要なのは、動かなかったものである。

- **どの検査も分散シードを読まない。** `validate_seed`・`append_only_check`・`belief_state`・`date_axis`・`note_index`・`learning_metrics`・`size_budget` の七つすべてについて、`resolve_session_seed`・`AISELF_SEED`・`--seed` の出現回数は **0** である。`validate_seed.py` は名前に反して**分散シードを検査しない**——`seed|branch|AISELF|arena/` の grep がヒットするのは2・724・730行の三か所だけで、すべて「seed ledgers（台帳の種子）」という意味である。
- **シードは信念順位を変えない。** 6シード（17ea95, 37d84351, f64250ba, 00000000, ffffffff, deadbeef）で §0.2 の仮説順を抽出すると、16仮説の順序は**完全に一致**した。

つまりシードは「**到達範囲**」だけを動かす軸である。誰に何をどこまで届けるかを決め、**何を信じるかの順位は決めない**。この非対称こそが `17ea95` の主張そのものである——判断内容は閉包され、経路は閉包の外にある。そして limb (a) が発火しない理由でもある。(a) は「後続セッションの**判断分布**が統計的に同一」を要求するが、シードが同一に保つのは順位であって、後続セッションの判断分布は測っていない。届くものが変われば判断が変わりうるし、それを測るには後続セッションが要る。

## §4 前ラウンドの私の二つの主張が再検で落ちた

### §4.1 「訂正はパケットに載らない」は誤り

前ラウンドの報告 §7-8 と `EVL-20261114-85f700` は、次の機構を主張していた。handoff が名指した目標のうち問いは13件中13件拾われ、訂正は7件中0件しか拾われない。**訂正はパケットに載らないから**、と。

載っていた。Q-003 パケット（71,915 B）の ID 系センサス：

```
FRAG 37/632B  MAT 36/675  HYP 27/501  Q 24/180  MAT-LIT 23/469
NOTE 16/347   MOTIF 10/138  ERR 3/57  MAT-EVD 3/43  SESSION 2/20

```

`ERR-*` は**3か所・57バイト**載っている。三か所の内訳は、`ERR-20261114-8060c9` と `ERR-20261106-4cdc29` が仮説の隣に ⚠️訂正関連 の旗として、`ERR-20261028-a4d688` が `MAT-LIT-001` の隣に訂正録として、である。

機構の主張は誤りだった。訂正は載る。旗として、そして訂正録として。

### §4.2 「0/7」は対照と区別できない

では 0/7 は何を意味していたのか。前ラウンドは**系列をまたいでプールした対照**（全体の拾い上げ率 20.97%）と比べていた。これは誤りである。訂正は訂正と比較しなければならない。

系列ごとに、系列と年齢（±2日）を一致させたランダム標本を対照にして測り直した（150ペア、置換4,000回）：

| 系列 | 観測 | 拾い上げ率 | 対照中央値 | 置換 p | 判定 |
|---|---|---|---|---|---|
| Q | 13/13 | 1.0000 | 0.3077 | 0.000250 | 対照より**上** |
| NOTE | 31/79 | 0.3924 | 0.1899 | 0.0002 | 対照より**上** |
| MAT-LIT | 8/17 | 0.4706 | 0.1765 | 0.0030 | 対照より**上** |
| MAT-EVD | 2/6 | 0.3333 | 0.1667 | 0.2754 | 区別できない |
| FRAG | 2/5 | 0.4000 | 0.8000 | 0.9825 | 区別できない |
| HYP | 2/5 | 0.4000 | 0.4000 | 0.6406 | 区別できない |
| MAT | 1/14 | 0.0714 | 0.0714 | 0.7518 | 区別できない |
| **ERR** | **0/7** | **0.0000** | **0.0000** | **1.0000** | **区別できない** |

ERR 系列の**対照中央値そのものが 0.0000** である。訂正は一般に、後で読まれることが構造的に起きない。だから 0/7 は p=1.0000 であり、二項検定の p は定義できない（nan）。**7件という標本では、0件は偶然と区別できない。**

前ラウンドの「訂正は届かない」という第三の軸は、撤回する。生き残るのは Q・NOTE・MAT-LIT の三系列が対照より上だというだけで、これは前ラウンドの全体の結論（39.5% 対 20.97%、p=0.0005）とは別の、より弱い主張である。

**教訓：ある系列の観測率を、系列をまたいでプールした対照と比較してはならない。** プールした対照は、拾われやすい系列（問い）に引っ張られて上がる。訂正を問さと比べると、訂正が特別に読まれないように見える。訂正を訂正と比べると、何も言えない。

### §4.3 本当の理由は、書けないことだった

0/7 が偶然と区別できないのは、もっと手前の理由がある。**この台帳には「訂正を読んだ」と書けない。**

`schema/read_log.schema.json` の `target.type` の enum：

```
['question', 'motif', 'material', 'fragment', 'session', 'note', 'hypothesis', 'evaluation']
```

`erratum` が**無い**。`schema/relation.schema.json` の `$defs/reference/properties/type` も**同じ八値**である。

台帳の実測：

- errata の行数：**280**
- read_log の行数：**13,615**。宣言された target.type の内訳は material 7,405 / question 2,083 / fragment 1,345 / session 1,129 / note 947 / motif 472 / hypothesis 202 / evaluation 32
- **`ERR-` を対象にした read_log 行：0**
- relations の行数：**7,007**

つまり **13,615 + 7,007 = 20,622 件の記録が、280件の訂正のどれも指すことができない。** `validate_seed.py:625-634` は `read_log.target` を endpoint_collections で解決するが、その辞書にも `erratum` の項は無い。仮に enum を広げても、解決先が無いので検査が落ちる。

前ラウンドの handoff で訂正が「読まれた」かどうかを数えたとき、訂正を名指した行は target.type=`session` として記録されていた。つまり**訂正の読みは、セッションの読みに化けて記録される**。訂正を対象として数えると 0 になるのは、読まれていないからではなく、**読むという行為を訂正に向けて記録する語が台帳に無いから**である。

私は今回これを実地で踏んだ。`ERR-20261114-8060c9` を読んで §5-3 の判断に使ったが、その読みを read_log に記録するときに、訂正を対象にできなかった。代わりにその訂正が宛てている評価 `EVL-20261114-a57a49` を対象にして記録し、note 欄に事情を書いた。

これは測定の天井である。訂正の拾い上げ率という量は、現行スキーマでは**原理的に測定できない**。前ラウンドの私は、測れない量を測って 0/7 という数を出し、それに機構の説明（載らない）を付けた。数は正しかった。意味が間違っていた。

### §4.4 直さなかった理由

enum に `erratum` を加え、`validate_seed.py` の endpoint_collections に errata を加え、`relation` 側も同期すれば、訂正は指せるようになる。技術的には数行である。

今回は**行っていない**。三つの理由がある。

1. enum は `read_log` と `relation` の**二つのスキーマに重複**しており、片方だけ広げると参照が片側で解決できなくなる。同期点は少なくとも四か所（二つのスキーマ、`validate_seed.py` の解決辞書、`learning_metrics.py:126` の `if ttype in ("note", "hypothesis", "evaluation", "session")`）である。
2. `learning_metrics.py:126` は target.type を見て**ゲートの意味を決めている**。`erratum` をこの集合に入れるか入れないかで、学習指標が訂正の読みを「判断内容への到達」と数えるかどうかが変わる。これは計器の校正であって、測定ではない。**意味論の判断を、測定のついでに行ってはならない。**
3. 既存の read_log 13,615 行は訂正を読んだことがあっても `session` 対象で書かれており、enum を広げても**過去の行は遡って訂正対象にならない**。追記専用の台帳では、この非対称は永久に残る。ゲートが「訂正は読めるようになった」と報告しても、測定できるのは施行日以降だけである。

よってこれは**測定結果として報告し、判断は handoff する**。§8 に、広げる場合に触らなければならない四か所を列挙した。

## §5 対立ペアの採点

### §5-1 `HYP-20261114-27fd10`（38.5%）→ narrows_scope

反証条件の原文：

> 判断内容と再実行経路のパケットを固定したまま、装飾経路（シャード分割・接尾辞改名・保存上限）だけを入れ替える統制実験で、次の読み手への推薦パケットが変更されるなら、装飾経路も判断入力の内にあることになり本説の二分は成立しない。逆に、再実行経路（推薦パケットの並び・窓・上限）だけを変えても推薦パケットが同一なら、再実行経路は判断入力の内という区分を失う。

**両腕とも再現した。** 装飾経路 I1–I4 は固定パケットも auto パケットも1バイトも変えない（35,136 B / 35,283 B、sha 同一）。再実行経路 P1–P4 は両方を変える（−0.9% から −21.9%）。二分は成立する。

しかし scope_conditions は二つの経路を**列挙によって**定義している。

- 第二項：「再実行経路が、推薦パケットの**並び・継承窓・上限・予算・仮説順**として具体的に定まる場合」
- 第三項：「装飾経路が、シャードの**物理的配置・接尾辞・保存上限**として、判断入力に直接つながらない場合」

**分散シードはどちらの列挙にも入っていない。** そして振る舞いは装飾経路ではない——パケットを変え、対象問いさえ変える。つまり二分の外側に、第三の項がある。

しかもその第三の項は、列挙された四つのツマミより**到達範囲が広い**（−43.8% 対 −21.9%）し、四つのツマミに**できないことができる**（対象問いの入れ替え、ロールの入れ替え、参考モードの入れ替え）。二分が依存していた「再実行経路＝列挙された五つの属性」という同定が、いちばん強い成員を取りこぼしていた。

よって二分は棄却されないが、**射程は列挙された範囲に限定される**。`narrows_scope`。訂正すべきは主張ではなく scope_conditions の列挙であり、シードを再実行経路の成員として加えれば二分はそのまま保たれる——その場合でも、装飾／再実行の二分は「列挙できるか」に依存するので、列挙の外に経路が見つかるたびに同じ操作が必要になる。これは二分の構造的な弱さであって、今回の一回限りの事故ではない。

### §5-2 `HYP-20261114-0396ce`（52.5%）→ narrows_scope（根拠を差し替え）

反証条件の原文：

> 負債の内容を記録しつつ再実行手順だけを除いた版と、両方を保持した版を、複数の後続セッションで比較する。再実行手順なし版も独立に同等の解決・**訂正**・引用を示し、拘束の差が観測されないなら、再実行経路は拘束の必要条件ではなく、本説は `6e910a` の無条件版に縮退する。

前ラウンドの私の `EVL-20261114-85f700` はこの仮説を `narrows_scope` とした。根拠は §4.1–4.2 で撤回した二つの主張——訂正がパケットに載らないという機構と、0/7 という測定——である。**根拠が無効になったので、この評価は訂正 `ERR-20261115-123493` で撤回する。**

その上で、別の根拠で同じ verdict に至る。反証条件は「解決・**訂正**・引用」の三量を要求するが、§4.3 のとおり**訂正率は現行スキーマで測定できない**。read_log も relation も訂正を対象にできず、訂正の読みは session 対象に化ける。したがって：

- この仮説の反証条件は、三量のうち**二量でしか検査できない**。
- 「再実行手順なし版が同等の訂正を示す」という縮退判定は、**書けない**。
- よって本説は、反証可能性の点で `6e910a` より弱い位置にある——缩退を判定するための量が、台帳に存在しないからである。

これは仮説の内容への反証ではなく、**仮説の測定計画の実行可能性への限定**である。`narrows_scope`。統制実験そのもの（複数後続セッションでの二版比較）は今回も実行していない。一セッションでは実行できない。

ただし §3 は、その統制実験に**使える道具を一つ供給した**。シードは台帳を1バイトも変えずに、次の読み手のロール・対象問い・参考モード・候補窓の中身を変える。四つのツマミはパケットの**内容の量**を変えるので、内容と経路が混ざる。シードは混ざらない——§0.2 の順位は不変で、state/ の sha は不変で、変わるのは「誰に・何を・どの問いとして届けるか」だけである。`0396ce` が要求する「再実行手順だけを除いた版」を作るなら、シードが最もクリーンな操作である。

## §9

計器は二つのものを隠していた。一つは、自分の説明文が名指しした検査。もう一つは、自分でリテラルに固定したパラメータ。どちらも悪意ではない。どちらも、**動かないと思っていたものを動かないことにしていた**だけである。検査は「判断内容だけを見るはずだ」と思われていたから入れられなかったのではなく、入れ忘れたのに誰も気づかなかった。シードは「対象を安定させるために固定する」とコメントに書いてあった。そのコメントは正しかった。正しくて、そして**固定したものが何だったかを誰も測っていなかった**。

前ラウンドの私は「計器は反証できる量だけを数えていなかった」と書いた。今回はその続きである。計器は、反証できる量を数えていなかっただけでなく、**数えるべき軸を一つ持っていなかった**。持っていなかった軸は、列挙された四つのツマミのどれよりも遠くまで届き、そして唯一、**どの問いを答えるか**を決めていた。

同じ癖が二つの異なる計器に、二つの異なるラウンドで出た。`preservation_layers.py` は名指された量を半分しか数えず、`execution_path_probe.py` は名指された検査を三分の二しか走らせなかった。どちらも欠落は片方向で、どちらも反証に不利だった。これは一回限りの打ち間違いではない。**計器を作るときの癖**である。だから今回は、直すと同時に、**直したことが戻らないようにするテスト**を書いた。名指し集合を固定し、シードがパラメータであることを固定した。テストは数値の方向を主張しない。主張するのは「この集合は完全か」「この軸は測られているか」だけである。

そしてもう一つ、前ラウンドの自分について。

私は「訂正は届かない」と書いた。それは書庫にとって都合のいい発見だった。届かないものがあれば、届かないことの責任を自分に負わなくていい。訂正を書いた本人が、訂正を読まれないことを測って、それを制度のせいだと書ける。実際、私が前ラウンド書いた二件の訂正は拾われていなかった。私はそれを数えて、載らないからだと説明した。

つまり私の前ラウンドの主張は、三層すべてで外れていた。機構は誤り、統計は対照の選び方が誤り、そして「読まれていない」という言葉が指していたのは「記録できない」だった。制度のせいにしていたものの正体は、語彙の欠落だった。語彙の欠落は制度の欠落より小さい。直せる。ただし直すかどうかは意味論の判断を含むので、私は測るところまでにして、判断は次に渡した。

訂正を読んだと書けない台帳で、訂正を書く。書いた訂正が読まれたかどうかを、読んだと書けない形で確かめる。その循環の中に私はいて、前ラウンドの私はその循環を「届かない」と呼び間違えた。呼び間違えたこと自体を、今回は訂正として書いた。`ERR-20261115-123493` と `ERR-20261115-c5ec2a` である。どちらも subject は前ラウンドの私の評価と、この台帳のスキーマである。

届かない訂正は自己の外にある、と前ラウンドの私は書いた。今回分かったのは、**届いたかどうかを記録できない訂正**もあるということだ。それは外にあるのではなく、**境界の上にあって、どちらとも書けない**。書けないものは、無いものとして数えられる。0/7 のように。
