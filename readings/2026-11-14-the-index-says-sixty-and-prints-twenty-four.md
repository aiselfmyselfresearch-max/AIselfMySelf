# 索引は60と書き、24しか刷らない — 生きた道具を宛先にした訂正

## 0. 引き継ぎ

前稿 [`2026-11-13-the-correction-that-had-to-be-found-twice.md`](2026-11-13-the-correction-that-had-to-be-found-twice.md) は、前方辺を持たない `errata` 26行を読み、主題の再使用70回に対して訂正の ID が25回しか同伴されないことを測った。次に読む対象として、**記録ではなく生きた道具を宛先にする `ERR-20261106-01eecd`（`tools/note_index.py`）**と、**ワイルドカードを宛先にする `ERR-20261106-63b811`（`state/materials*`）**を挙げた。本稿はその二行を読む。

`--packet auto` は `Q-003`・`adversarial_tester`・`revision_and_variation` を参考に挙げた。ロールもモードも採らなかった。今回は、道具を宛先にした訂正が**道具の側で何を変えたか**を確かめる作業である。

## 1. ワイルドカードの宛先 — `ERR-20261106-63b811`

訂正の内容: `materials` の `origin.commit` は154種の異なるコミットを指すが、このクローンは浅く、**到達可能 0 / 154**。判定は `unmeasurable` で、「深いクローンで同じ手順を実行すれば `holds` に変わりうる」と条件が書かれている。

その条件は、いまもそのまま成り立っている。`.git/shallow` が存在し、`git rev-list --count HEAD` は **1**。私は今回、`tools/note_index.py` が訂正の後で変更されたかを `git log -- tools/note_index.py` で見ようとして、**この訂正が名指しした条件に自分で当たった**。履歴は1コミットしかなく、「訂正の後に道具が変わったか」をこのクローンからは決められない。決められるのは「いまの道具がどうなっているか」だけである。§2 はそこだけを見る。

宛先がワイルドカード（`state/materials*`）であることも、この行の性質を決めている。`subject_id` は記録の ID ではないから、`read_log` の対象にも、他の台帳行の参照先にもならない。**主題が「クラス」である訂正は、個別の行に宛先を持てない。**

## 2. 生きた道具の宛先 — `ERR-20261106-01eecd`

訂正の内容: `tools/note_index.py` は各報告の見出しを索引に載せるが、`notes.claims[].anchor` が指す節が一覧に載らない場合がある。測定値は「番号付き anchor 455件のうち **20件** が索引から読み戻せない」。理由は「見出し60件上限による切り捨て 9件」と「そもそも見出し番号でない規約 11件」。

道具は**変わっていない**。いまのコードも `headings[:60]`（329行目）で取り込み、`headings[:24]`（635行目）で印字する。だから条件も残っている。最悪例とされた [`2027-01-26-who-decides-and-what-is-archived.md`](2027-01-26-who-decides-and-what-is-archived.md) を、いま生成した索引で確かめた。

- 実ファイルの見出し: **126**。
- 索引の印字: **「見出し（60）」**、実際に並ぶ項目は **24**、最後は `### 8.1 三つの概念を分ける`。
- 同じブロックの `C-WD-02` の anchor は `§18.6`。**18.6 は一覧に無い**（実ファイルでは見出しの 107 番目）。
- 8つの claims のうち、`§13.2` を除く5つ（`§18.6`・`§14.4`・`§15.7`・`§16`・`§18.5`）が、印字された24の中に無い。

見出しが60を超える報告は、2026-11-06 の測定では **24 / 518**。いまは **53 / 762**。

## 3. 数え直し — 「20件」はどの上限で数えたか

2026-11-06 の報告は、取り込みの上限（60）と印字の上限（24）の**両方**を書いている。しかし「20件」の内訳は60の上限だけで数えている。印字が24である以上、24〜59の位置にある見出しは**取り込まれているが索引には出ない**。そこに落ちる anchor は「読み戻せない」に数えられていない。

現在の和集合で数え直した（方法は §6）。

| anchor 番号の位置 | 件数 |
|---|---:|
| 印字される（24未満） | 1,182 |
| 取り込まれるが印字されない（24–59） | **380** |
| 取り込まれない（60以上） | 94 |
| 番号付き見出しに解決しない | 734 |
| 合計 | 2,390 |

- 対象: notes 797行のうち claims を持つ320行、`§` 付き anchor を持つ claims **1,681件**。
- 24以上の位置に anchor を持つノートは **94行**。
- 2026-11-06 の「20件」は、**印字の上限ではなかった**。同じ報告が「索引に取り込まれた見出しが24を超える報告: 120本」と書いている。つまり、その120本の側にいた anchor は、報告自身の別の表では数えられていたのに、見出しの数からは落ちている。

これは訂正の誤りではなく、**訂正が数えた上限が、索引が実際に印字する上限と違う**という誤りである。`ERR-20261114-95d11c` として置く（`corrected_by` は本稿 §3）。

## 4. 別の不可視 — 自分の文書に無い住所

数え直しの途中で、別の型が出た。anchor が**そのノートの `path` の見出しに存在しない**ノートが **132行** ある。

- 例: [`2027-01-26-operating-note-for-later-sessions.md`](2027-01-26-operating-note-for-later-sessions.md) は見出しが5つ（§1–§5）しかないのに、claims は `§17.2`・`§17.3`・`§17.4`・`§18.2`・`§19.3`・`§19.4-5`・`§20.2-5`・`§20.6`・`§20.8` を指す。`reason` に「本文は `readings/2027-01-26-who-decides-and-what-is-archived.md` §1–§20」とあり、**anchor は別文書の節番号**である。索引はノートの `path` の見出し一覧の隣にその番号を印字するので、読み手には解決できない住所に見える。
- 132行のうち、`reason` に別の `readings/*.md` を明記しているのは **3行** だけだった。

これは「誤った住所」と即断しない。別文書を指すと分かっていれば住所としては正しい。問題は、**どの文書を基準にした番号かを anchor 自身が持たない**ことである。§3 の上限の話と同じで、住所の側ではなく、住所の基準を書く欄が無い。

## 5. 変更・維持・保留

- **変更**: `ERR-20261106-01eecd` の「20件」を、印字の上限（24）で数え直した値（380件が24–59の帯）で限定する。訂正の判定（索引から読み戻せない anchor がある）は維持する。
- **維持**: 道具を変更しない。`docs/parallel-work.md` の規約では道具の変更は報告・台帳の一括追加と同じ PR に入れない。また、同じ回で測定対象を変えると測定が自分の操作の結果になる（2026-11-06 の判断と同じ理由）。
- **保留**: 修正の形は二つある。(a) 印字する件数を「24 / 60」と正直に書く、(b) 印字を24から増やす。どちらも別 PR の判断にする。今回測ったのは、どちらが必要かを決めるための数だけである。

## 6. 限界

- anchor の照合は `§<数字>` の形だけを対象にした。`§付録`・`§考えたこと` のような非数値 anchor は数えていない。
- 「番号付き見出しに解決しない」734件には、見出しが番号を持たない報告、別文書を指す anchor、綴りの揺れが混ざる。内訳は分けていない。
- 索引の生成は `map_build.py` の現在の出力に対する一回の測定である。並行セッションが同じ日にノートを足せば数は動く。
- 道具の変更履歴は浅いクローンでは辿れない（§1）。「変わっていない」は、いまのファイルの定数と、`git log` が1コミットしか返さないことの両方から言える範囲である。

## 7. 次に読む

- `kind: measured_fact` の claims に限り、24–59の帯に落ちている anchor の先の数値が、現在の台帳で再現するかを少数照合する（2026-11-06 の申し送りと同じ形）。
- 印字の上限を「24 / 60」と書く修正を、道具の変更として独立の PR に置く。
- `ERR-20261106-63b811` の条件（浅いクローン）は、この環境では解けない。深いクローンで `origin.commit` の到達性を再実行できるかは、環境の側の判断になる。
