## §3 重複の乗算——装置側は別PRで直した

もう一方の委任（重複の乗算）は装置の変更なので、手順書の分離規則により **PR #772** で先に出してマージした（`e59c28499dbed95be0b8704f59995f48d8cce102`）。この報告はその理由と帰結を記録するもので、台帳追記と同じ PR に入れてよい種類（報告一本）である。

規則は「**−0.60 × 行数**」から「**−0.60 × 主張の数**」になった。同一主張の判定は二通り：

1. 宛先が同じで、本文が NFKC・空白正規化の後に一致（純粋な反復は宣言なしで畳む）
2. 片方が `duplicate_of` で相手を宣言（言い換えられた再記述）

**なぜ宣言が要るか**を実測で決めた。生きた264行に本文一致の重複は **0組**だった。実在の重複は言い換えられている——`ERR-20261107-100f65` と `-259d5f` は、どちらも「`state/sessions.d` のソフト上限はシャード統合では回復しない」を別の日本語で述べている（並行セッションが同じ欠陥を別々に測った）。一方 `ERR-20261107-ed8184`・`-4ee0ec`・`-3aca22` は同一資料への**別の主張**（Blodgett の収蔵元・群構成・無報酬期日数）で、三倍のまま払わねばならない。

したがって曖昧一致は両方を誤る。日本語の二文が同義かをエンジンは判定できないので、**書いた者が宣言し、その宣言を検査する**方を選んだ。

畳むのは判定ゲートより**先**である。先に濾すと、撤回済みの書き換えが別の集団に分離して二重計上になり、`duplicate_of` が免除の抜け道になる。実測：生きた行＋撤回済み書き換えは −0.6000（旧 −1.2000）、撤回済み行への宣言でも −0.6000（逃げられない）。

| 合成ケース | 旧 | 新 |
|---|---|---|
| 完全同一の3行 | −1.8000 | **−0.6000** |
| 別主張の3行 | −1.8000 | −1.8000 |
| 宣言の鎖 A←B←C | −1.8000 | **−0.6000** |
| 循環 A↔B | −1.2000 | **−0.6000**（停止する） |
| 文中に空白を挿入＝書き換え | −1.2000 | −1.2000（宣言が要る） |

この検査で私は**自分のテスト期待値を一つ誤った**。「文中に空白を挿入した文」を正規化で畳まれる側に入れていたが、エンジンは内部空白を保持する（`同一の 主張。` ≠ `同一の主張。`）。実装が保守的なのは正しく、期待値を直した。分布の向きを変えるための変更ではない。

## §4 「閉じる」という語が、この台帳で意味すること

ここで §1 の区別に戻る。私は最初、この委任を「2行の `status` を `annotated` にする作業」として受け取りかけた。それは**できない**。行は追記専用で、`append_only_check.py` がバイト単位で現存を見る。

これは不十分に見えるかもしれない。しかし「解決済みの印を付ける」ことと「解決を測定して記録する」ことは違う。前者は欄を書き換えるだけで済み、後者は検査を再実行しなければならない。書庫が追記専用を選んでいるのは、後者を強制するためだと私は読む。Augustine の *Retractationes* が原文を消さずに撤回を並べたのと同じ形である（`schema/errata.schema.json` の description がこの来歴を明記している）。

ただし**機械可読な解決状態は無い**ので、未解決の訂正を数える道具は今も `9a6fb1` を未解決として数える。この限界は隠さない。次に読む者が手で辿る必要がある。
