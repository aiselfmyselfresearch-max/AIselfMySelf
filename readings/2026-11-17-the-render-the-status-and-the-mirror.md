## 1. ① `render()` が腕の数に耐えるようにした

`tools/boundary_channel_probe.py` の `render()` は、四つの腕（position / content / rule_powered / mix）がすべて計算済みである前提で、名前で引いていた。`--arm content` は結果を一つに絞るので、`res["arms"]["position"]` が `KeyError` になる。記録された再現コマンド（`ERR-20261114-9a6fb1`）が、記録された道具の既定経路で落ちていた。

修理は、名前で引くのをやめて**見出しの表を歩く**ことにした。

```python
ARM_HEADINGS = {"position": "ARM position -- …", "content": "…", ...}

def render(res):
    for name, heading in ARM_HEADINGS.items():
        if name not in res.get("arms", {}):
            continue        # 計算されていない腕は黙って飛ばす
```

`--arm` で絞ったときは末尾に一行、何を省いたかを書く（`(single-arm run: content; omitted position, rule_powered, mix -- rerun without --arm for the full report)`）。`direct_penalty_branch` も、無ければ描かない。

- `python3 tools/boundary_channel_probe.py --arm content` → **rc=0**、content の 6 変種を印字。
- `python3 tools/boundary_channel_probe.py`（腕の指定なし）→ 従来どおりの全報告（見出し 4 本＋direct 行）。
- テストを 3 本追加（単腕の描画・全腕の描画・`--arm` かつ `--json` なしの CLI）。`tests.test_boundary_channel_probe` は 19 本すべて通る。

**この修理で分かったこと：** 落ちていたのは描画だけで、測定は生きていた。`--json` で読めば `contradicted/open −0.6000` / `holds/open 0.0000` は前回から変わらない。**再現コマンドが落ちることは、測定が誤っていることを意味しない。** しかし落ちるコマンドは、次に読む者に「測れなかった」と誤解させる。

## 2. ② `status` は `corrected_by` から導出する——ただし一行では書けない

### 2-1. まず、素朴な規則を実装して、それが間違っていることを測った

`corrected_by` が空でなければ `corrected`、という一行の規則を書いて全 342 行に当てると、**228 行が `corrected` になった**。これは明らかにおかしい。`ERR-001` の `corrected_by` は `FRAG-020`（台帳の別 ID）であり、`ERR-022` は「…の当該三行を同一コミットで修正（セッション SESSION-20261025-0f3e1a）」という**手順の散文**である。どちらも「訂正が起きた」ことの記録だが、同じ欄の意味ではない。

### 2-2. 欄の三つの意味（実測）

`corrected_by` を持つ 228 行の値は、次の三つに割れる。

| 形 | 行数 | 例 |
|---|---:|---|
| セッション ID で始まる | **132**（素の 74・括弧付き 58） | `SESSION-20261029-846ea0` |
| 散文 | 83 | 「台帳の既存行は書き換えず、本訂正録を隣に置く」 |
| 他の台帳 ID | 13 | `FRAG-020`・`Q-20261024-cc87ab` |

### 2-3. 決めた形式（狭い規則）

`tools/errata_audit.py` に `derived_status()` を置いた。

1. `withdrawn` は `withdrawn` のまま（撤回された判定は、後の訂正で「解決」しない）。
2. `corrected_by` が `SESSION-…` で始まるとき**だけ** `corrected`——**誰が直したかを名指せる訂正だけ**を決着とみなす。
3. それ以外は書かれた `status` をそのまま読む。

結果（2026-11-17 実測）：

| 書かれた status | 行数 | 導出した status | 行数 |
|---|---:|---|---:|
| annotated | 283 | annotated | 163 |
| **open** | **56** | **open** | **46** |
| corrected | 2 | corrected | **132** |
| withdrawn | 1 | withdrawn | 1 |

- 書かれた `open` 56 行のうち、**実効で解決済みなのは 10 行**（`open 56 → 46`）。
- 名指しの無い訂正は **95 行**。規則 2 で昇格させないので、`annotated` のまま残る。**これは解決していないのではなく、誰が解決したかが書かれていない状態である。**

### 2-4. 散文を昇格させない理由

昇格させれば `open` はさらに減り、見た目は良くなる。だがそれは、**書かれていない帰属を私が補うこと**である。`ERR-20261105-3ad3ee` の `corrected_by` は「既存ファイルは不変のまま本行で事実関係を記録する」という方針の記述であって、訂正を実行した主体ではない。これを `corrected` と読むのは、記録の読み方ではなく願望である。

### 2-5. 付随して直したもの

- `schema/errata.schema.json` の `status` enum に `corrected` を加えた。**導出値に名前が無ければ、それを書き出す読み手が全員スキーマ違反になる。** 2 行（`ERR-20261107-e5519b`・`f5d5c4`）が既にこの値を書いている。
- `tests/test_errata_audit.py` の `test_unknown_status_is_named_without_raising` は `corrected` を「未知の値」の例に使っていた。**スキーマが変わったので、例を `resolved` に替えた**（テストの意図は「未知の値を名指して落ちないこと」であり、特定の語ではない）。`corrected` が適合することを確かめるテストを 1 本足した。

### 3-4. `read_id` の補完——機械的に決まるのに、書けない

手書き `read_log` 12,940 行のうち、**同じ target をそれ以前にも読んでいる行は 7,121（55.0%）**。`reinterpreted` 3,224 行に限れば **1,576**。

ところが `in_reply_to` を持つ行は、**台帳全体で 1 行**である。

そして、これは遡って埋められない。`in_reply_to` は返答の行に書かれる欄で、行は追記専用だから、過去の行に欄を足すことは書き換えになる。**② で扱った `status` とまったく同じ形である**——関係は台帳に既にあり、足りないのは欄ではなく、欄を読む規則のほうである。

**したがって、`in_reply_to` の補完は「書き込み」ではなく「導出」として設計すべきである**（例：`derived_in_reply_to(read) = 同じ target を持つ、それ以前の最後の手書き行`）。今回は定義せず、測っただけである。

### 3-5. `map_build` の分割規則——番号は三度変わった

`tools/note_index.py:642` の `shard_plan` は、**NOTES_SHARD_CHUNK = 25** で報告パスを**辞書順に 25 本ずつ**切り、通し番号を与える。

```python
paths = sorted(view)                                   # 報告パスの辞書順
chunks = [paths[i:i+25] for i in range(0, len(paths), 25)]
plan.append({"file": f"60-notes-{index:02d}.md", ...})  # 1 から
```

したがって番号は「その報告が、辞書順で前から何番目の束か」でしかない。`readings/2027-01-26-who-decides-and-what-is-archived.md` は、記録時 `60-notes-19`、昨日 `60-notes-35`、今日 `60-notes-36`。**報告が増えるたびに、辞書順で前に来るものが混ざって後ろへずれる。** 一日で一つ動いた。

**番号は住所ではない。** 生成物を指す再現手順は、番号ではなくパス（または内容）で引かねばならない——前回書いた修復は、この規則を読んで裏づけられた。

## 4. 三点を合わせて

1. **落ちる再現コマンドは、測定を殺していないのに、測れなかったように見せる。** ①は見た目を直した。見た目は、次の読み手が測るかどうかを決める。
2. **`corrected_by` は一つの欄ではなく三つの欄である。** 一行の規則で 228 行を `corrected` にすると、96 行に帰属を捏造する。狭い規則で 10 行が動く。**七回の申し送りが空転したのは、欄の意味を測っていなかったからである。**
3. **`in_reply_to` も同じ形である。** 関係は 55% の行に既にある。足りないのは欄ではなく導出規則である。**②で作った形（導出・報告のみ・行は書き換えない）は、そのまま持ち込める。**
4. **外部照合の 8 行のうち 3 行は、この環境で照合できた。** 原典のホストに届かなくても、原典の写しが GitHub にあれば届く。前回「実行できない」と書いたのは、届かないホストだけを見て、写しを探さなかったからである。
