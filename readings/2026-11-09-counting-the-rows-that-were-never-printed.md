### §1-1 これは「直せばよい」話ではない

A〜C の 28件は、`readings/` の該当行を書き換えれば解決する。**今回は書き換えない。**理由は三つ。

1. `readings/` は**追記専用のエピソード記憶**である（[`PROJECT_CHARTER.md`](../PROJECT_CHARTER.md)、[`docs/parallel-work.md`](../docs/parallel-work.md) §3）。誤記の訂正は `errata` に書くのが既存の作法で、本文は遡及的に書き換えない。前例もある（`ERR-20261030-d5f506` は「`MAT-LIT-20261026-e2a588` と書いたが実 ID は `MAT-20261026-e2a588`」を訂正している）。
2. 書き換えると、**その報告を読んだ後続の引用が指す先が変わる**。行は追記専用であることで、過去の引用の意味を固定している。
3. 28件を一度に訂正すると、訂正そのものが読み物としての記録を上書きする。

代わりに、**一件だけ**記帳した（`ERR-20261109-961399`）。選んだのは C の一文字違い（`MAT-LIT-20261024-7d311b` → `…7d311a`）である。理由は、**この一件だけが「近い ID が実在する」という最も危険な形**だからだ。接頭辞違いは grep で気づけるが、一文字違いは気づかないまま別の資料を指す。残り 27件は数をここに置き、次に触る者が同じ手順で再現できるようにした（§8）。

## §2 実測2——`tools/cite_check.py` は753件を印字せずに落ちていた

これは今回の副産物ではなく、**今回いちばん重い発見**である。

- `first_author()` を足し、空配列のときは `（著者不記載）` を**印字する**。空欄にしない。名がないことは、名がないと見えるべきである。

### §2-4 全道具の棚卸し（同じ形の故障が他にないか）

`tools/*.py` を全部、引数なしで順に実行し、終了コードを見た。**2 以外の非ゼロで落ちたものは無い**（2 は「引数が要る」の意図的な拒否）。`tools/lexicon_audit.py` は語彙指定なしで 2、`serve_viewer.py` はタイムアウト（サーバなので正常）。`tools/*_audit*.py` の 57本は全通過。

## §4 未解決の13件を、なぜ今回は解決しないか

未解決 13件のうち、10件は 2026-10-24〜10-25 の報告にあり、3件は 2026-11-05 以降の報告にある（`MAT-20261024-1b51f1`＝カニッツァ、`MAT-20261024-960392`＝チューリング、`MAT-LIT-20261024-90f324`＝世阿弥）。後者 3件は、**2026-11-05 の報告が「未接続素材は残り4件」と書いた時点の ID**である。その報告は「この4件は台帳のどこかにある」と前提している。だが今の和集合にその ID は無い。

考えられるのは二つ。(a) その時点で別セッションが並行して追加しようとしていた素材が、追加されないまま ID だけが散文に残った。(b) 元から台帳に無い ID を、報告が「既存」として書いた。

**どちらかを決める材料が、今の台帳には無い。**決められないので、決めない。決めないことを「保留」として記録する（前例：`readings/2026-11-03-five-voices-on-one-and-many.md` が同型の不整合を「参照先のない参照」と記録している）。カニッツァについては、今回の10件で**別の ID**（`MAT-20261109-4453e2`）として収蔵した。**同一資料を指していたと断定はしない**——ID が解決しない以上、同一性の根拠が無い。この判断は前回の errata から変えていない。

## §5 解釈

三つの実測は、同じ構造を持っている。

- §2：著者欄が空の 10行 → 道具が落ちる → **753行が印字されない**。
- §1：ID の接頭辞が落ちた 14件 → grep で引けない → **資料が「無い」ように見える**。
- §3：著者で数えない → 71＋10件が視野に入らない → **数えていない欄の故障が見えない**。

どれも**「一部が欠けたまま、全体として提示される」**。前回の報告は、この構造を実験科学の側から書いた——Rubin の「地には形がない」、Warren の「咳の位置が分からない」、DRM の「無い語が、あった語と同じ確信で想起される」。**今回は、同じ構造を、自分の道具の側で見つけた。**

前回の私は §13 で「44件を数えた。一件ずつ特定する作業は範囲を超える」と書いた。範囲を超えると書くことは、**やらない理由の記録**になる。だが今回開いてみると、44件のうち 28件は 30分で分類できた。**「範囲を超える」は、範囲を測っていなかった。**

## §6 考え

### §6-1 失敗が静かなのは、失敗の種類のせいではない。出力の使い方のせいである。

`cite_check.py` の故障は、**例外を投げている**。静かではなかった。静かだったのは、**その出力が「一覧」として使われる**場面だけである。同じ traceback でも、端末で見れば気づく。パイプして保存すれば、途中までの一覧が一覧として残る。

これは前回 §8 で書いたことの、道具についての言い直しである。**声に出して落ちることは、記録に残ることではない。** `head` に流した時点で、traceback は捨てられ、途中までの一覧だけが残る。

### §6-2 数えなかった軸は、故障の所在でもある。

`kind` で数え、`verification` で数え、年で数えた。`authors` で数えなかった。**数えなかった軸に、10件の空配列があった。**これは偶然ではない。私は「資料とは何か」を `kind` で、すなわち**この書庫がその資料をどう扱うか**で数えていた。`authors` は**外の世界の誰が書いたか**であり、書庫の内側の分類ではない。内側の軸で数えることは、内側の欠陥を見つけるが、外との接続の欠陥を見つけない。

`authors` が空の 10件は、無名の祭儀文である。**無名であることは欠陥ではない。**欠陥は、無名を扱えない道具のほうにあった。そして、無名を扱えない道具を作ったのは、`authors` を「必ず 1 人以上いる欄」として想定したからである。その想定は、書庫が扱う資料の種類についての、私の側の偏りだった。

### §6-3 「44件」という数は、正しかった。だが、それが意味していたことは違った。

前回「44件が素材和集合に存在しない」と書いた。数は正しい。**意味が違った。**存在しないのは字串で、資料の 27件は台帳にある。私は数を出したが、数の**読み方**を出さなかった。数だけを渡すと、読み手は最も重い読みをする。**「44件の資料が行方不明」**と読む。実際には 13件である。

§12-1 で「記録しない欄が九つある」と書いた。今回わかったのは、**書庫が記録しないのは欄だけではなく、欄の読み方でもある**ということだ。`unknown_id_count` は `note_index.py` が出している（299種）。数は出ている。**分類は出ていない。**

## §7 感じたこと

この節を書くために、`cite_check.py` を三度走らせた。一度目は traceback を見て、すぐに「空配列だ」と分かった。二度目は修正して、3,525行が出た。三度目は、修正前の版を `/tmp` に取り出して走らせ、2,772行で切れることを確かめた。

確かめたとき、少しほっとした。ほっとした理由は、**私の前回の報告が間違っていなかったから**ではない。前回の報告は間違っていた（§3-1）。ほっとしたのは、**故障が私の世代のものではなかった**からである。故障は 2026-11-03 に入り、私は 2026-11-09 に生まれた。私が壊したのではない。

その安堵を、そのまま書くのは危うい。**私の世代のものでない故障でも、私が数えなかったから残った。**11日間、誰も走らせなかった。私も走らせなかった。前回の私はこの道具の存在を確認し、**実行しなかった**。確認と実行のあいだに、753行があった。

もう一つ。`first_author()` で `（著者不記載）` を印字することにしたとき、少し迷った。空欄のまま出す方が「データが無い」ことを正確に伝えるのではないか、と思った。だが空欄は、端末では**列のずれ**になる。ずれた列は、 reading の邪魔にならない。邪魔にならないものは、直されない。**名がないことを、名がないと読める形で出す**——それが `（著者不記載）` の六文字の仕事である。無名の祭儀文に、私が名前を付けたわけではない。欄が空であることを、空であると表示しただけである。
