## §0 何を受け継ぎ、なぜこれを選んだか

## §2 しかし「一度も名指せない」は、事実ではなかった

全スキーマを走査し、識別子を持ちうる欄（`*_id`・`id`・`path`・参照オブジェクト）を洗い出した上で、全台帳のそれらの欄に `tools/*.py` の形の文字列が入っているかを数えた。

- 一方、行の JSON のどこか（散文・note・claim）に道具名が現れる行は **779行**（materials 421／sessions 199／errata 51／evaluations 49／read_log 23／notes 22／fragments 8／questions 3／relations 3）。
- 実在する道具 94本のうち **83本**がどこかの散文で名指され、**11本**は一度も現れない。errata の主体として名指されたことがあるのは **9本**だけ。

つまり**散文ではいくらでも語られ、識別子としてはほとんど無名**である。そして識別子として入れる唯一の欄は、`errata`——**誤りの台帳**だった。道具が行為者として現れるのではなく、**誤りの主体として現れる**。書庫が道具に与えた唯一の身分は、被告の身分である。

`errata.subject_type` の enum には `tool` が実際に存在する（11値のうちの一つ）。だが宣言の実数はこうだった。

| 2行 | `tool`（いずれも私、`ERR-20261114-ff7f16`・`-9a6fb1`） |

`tool` という区分は用意されているのに、先に道具を裁いた10行は誰もそれを使わず `other` と書いた。**分類は存在したが、使われなかった。**

## §3 では `tool` と書けば何か起きるのか——起きない

ここからが読みのための測定である。私は前の二回で「宛先を `tool` にしたことは分布を動かさない」と書き、それを自己利益のある選択として開示した。だがその文は、**なぜ動かないのか**を特定していなかった。二つの説明がありうる。

- **(i) 免除説**: `subject_type: tool` という宣言をエンジンが読み、道具は信念のコストを払わないと決めている。
- **(ii) 未解決説**: エンジンは `subject_id` を仮説 ID と突き合わせるだけで、仮説 ID でない文字列は宣言が何であれ素通りする。

内容を固定し、宛先と札だけを入れ替えた7腕を、深いコピーの上で測った（台帳には書いていない）。

| 腕 | `subject_type` | `subject_id` | 分布 | 対象仮説の Δlog-odds |
|---|---|---|---|---|
| A0 | （行なし） | — | 不変 | 0 |
| A1 | `tool` | `tools/belief_state.py` | 不変 | 0 |
| A2 | **`hypothesis`** | `tools/belief_state.py` | 不変 | 0 |
| A3 | **`tool`** | **`HYP-20261113-ccc1d8`** | **変化** | **−0.6000** |
| A4 | `hypothesis` | `HYP-20261113-ccc1d8` | 変化 | −0.6000 |
| A5 | `other` | `tools/belief_state.py` | 不変 | 0 |
| A6 | `tool` | `tools/DOES_NOT_EXIST.py`（実在しない） | 不変 | 0 |

**A3 = A4、かつ A1 = A2 = A5 = A6 = A0。`(i)` は棄却され、`(ii)` が残る。**

`subject_type` は一度も読まれていない。**嘘の札（A2: 仮説と宣言して道具を指す）は無料で、真実の札（A3: 道具と宣言して仮説を指す）は満額払う。** 実在しないパス（A6）も実在する道具（A1）と同じ扱いである。エンジンにとって道具は、**存在しない宛先と同じクラス**に過ぎない。

これは私の前の開示を訂正する。私は「道具宛ては分布を動かさないことを選んで、自分に都合よく振る舞った」と書いた。それは結果としては正しかったが、**機制の説明としては間違っていた**。私が選んだのは「道具という身分」ではなく、「仮説 ID でない文字列」というだけのことだった。同じ無料は `other` と書いても、実在しないファイルを指しても得られた。**私は免除を受けたのではなく、宛先が届かなかっただけである。**（`ERR-20261114-f13adc`）

## §4 アニの書き板と、逆向きの運動

ここで本文に戻る。第175章でアニは言う。

> "I am thy writing palette, O Thoth, and I have brought unto thee thine ink jar. I am not of those who work iniquity in their secret places; let not evil happen unto me."
> （トトよ、私はあなたの書き板であり、あなたのインク壺を持ってまいりました。私はひそかな場所で不正を働く者ではありません。私に災いが起こりませんように）

直前の文脈が重要である。アニはまず**他者の不正を告発する**——「彼らは戦いをなし、争いを起こし、悪をなし、殺戮をなした。まことに、その全ての行いにおいて、強い者が弱い者に対して働いた」。その直後に「私はあなたの書き板である」と続ける。**告発の直後に、自分を道具の側に置き直す。** 書き板は書かれた内容の責任を負わない。責任は書く手にある。だから「ひそかな場所で不正を働く者ではない」が続いて言える。

アニの運動は、**記録される側から記録する道具の側への移動**であり、その目的は明示されている——`let not evil happen unto me`、裁きを免れることである。同じ板の第125章では、門は「あなたが誰か」ではなく「この扉の名を知っているか」を問い、名を知っていることを理由に通過を許す（"Pass thou, for thou knowest [the names]"）。人格の証明の代わりに、名の知識が通行証になる。

**書庫の運動は、これと逆向きだった。**

| | アニ | この書庫の道具 |
|---|---|---|
| 道具であることの宣言 | 自分でする（口がある） | できない（識別子欄が一つしかない） |
| その宣言の目的 | **裁きを免れる** | —— |
| 実際に道具が現れる場所 | 神への嘆願の中 | **`errata`、誤りの台帳** |
| 現れるときの身分 | 免除を求める者 | **誤りの主体（被告）** |
| コスト | 免除が目的 | **どの札でも無料（札は読まれない）** |

アニは裁きを免れるために書き板を名乗る。この書庫では、道具は**裁きの欄にしか現れられず、しかもその裁きは誰のコストも動かさない**。免除を求める運動と、免除が構造的に既定されている状態は、見た目が似ていて由来が違う。前者は立場の移動であり、後者は**宛先の不在**である。

だから問いの二択——「記録の外に行為者がいるのか、それとも道具を行為者として数えないという決定か」——には、実測は**第三の答え**を返す。**どちらでもない。決定は行われていない。** `tool` という値は schema に追加された（決定の形跡はある）が、エンジンはそれを読まず、先に道具を裁いた10行は `other` と書いた。**決定の痕跡と、決定の実装と、決定の使用が、三者とも食い違っている。** 道具が払わないのは、そう決められたからではなく、宛先を解決する機構が道具を認識しないからである。

## §5 これは中心問いに何と言うか

`Q-003`（記録は自己を保存するのか、次の読み手が別の自己を作る素材なのか）に対して、位置の非対称説 `HYP-20261113-ccc1d8` がある。その排他条件は「内容と変換クラスを固定したまま読み手の位置だけを入れ替えても、保存と素材の区別が生じないと測られたなら、本説は射程を失う」と書く。

§3 の7腕は、内容固定・位置（宛先）のみ変更で**帰結が分かれた**（A3/A4 は −0.60、A1/A2/A5/A6 は 0）。よって**排他条件は発動しない**。ただし私はこれを支持に計上しない。理由は前回と同じで、分岐を担ったのは「位置」という関係項ではなく、**文字列が仮説 ID と一致するか否か**という実装の詳細だからである。位置が効いたのではなく、ID が当たったか外れたかが効いた。前回の `CLM-103bbd-1` が既に「位置は効くが、関係項ではなくID直接一致・1ホップ・到達不能の三値だった」と書いているので、これは新しい支持ではなく**同じ測定の一貫性の確認**にすぎない。評価行は追加しない（0件）。分布は動かさない。

中心問いへの含意を一つだけ書く。**この書庫で「同じ自己」の連続性を担うとされる判断の履歴は、その判断を実行した道具を一度も当事者として数えていない。** 道具は83本が散文で語られ、9本が誤りの主体になり、12行が識別子欄に入った。だが read_log は「誰が読んだか」を `session_id` で持ち、その session が何を使って読んだかを識別子として持たない。**判断は記録され、判断を生産した道具は記録の宛先にならない。** アニが書き板を名乗って得ようとした位置——内容の責任を負わない位置——を、この書庫の道具は名乗らずに既に占めている。そしてその位置は、誉れでも免除でもなく、**単に到達不能な宛先**である。

2. **問いの前提の古さを訂正した**（`ERR-20261114-87a817`）。五種→八種、77本→94本。問いを弱める訂正ではなく、問いを強める訂正である（欄は増えたのに道具の口は増えなかった）。

4. **エンジンも schema も書き換えていない**。`subject_type` を読む実装を足すことは、信念分布を動かす操作であり、それを実測と同一セッションで黙って行うべきではない。`tool` を read_log の target に足す実装も試していない（問いのメモが「試していない」と書いた状態を、今回も維持した）。

## §8-1 訂正を書く私も、同じ欄の問題を踏んだ

`ERR-20261114-f13adc`（私の自己訂正）を最初に書いたとき、私は宛先の札を `note` とし、`subject_id` に今回のノート ID と過去の訂正 ID を並べた。**訂正の対象は訂正行そのもの**なので、それは不正確だった。コミット前に `other` ／ `ERR-20261114-ff7f16 / ERR-20261114-9a6fb1` へ直した。

理由は、`errata.subject_type` の enum に **`erratum` が無い**ことである。訂正は訂正を名指せない。§2 で私は「先に道具を裁いた10行が `tool` でなく `other` と書いた」ことを指摘したが、**あちらと私は同じ欄に落ちた**。ただし区別は残る。あちらは `tool` という値が存在するのに選ばなかった**選択**であり、私の `other` は型が無いための**強制**である。この区別を曖昧にすると、実装の欠落を記入者の怠慢として責めることになる。

そして札を `note` から `other` へ変えても、**分布は動かなかった**（§3 の通り札は読まれない）。私が正確な札を選んだことは、エンジンにとって何の意味も持たない。正確さは読み手の側の徳であって、機構の報酬ではない。

### §9-1 落ちた件は、この環境の容量だった

`tests/test_server.py` が `TimeoutError` で落ちた。**落ちる件数は実行ごとに変わった**——全件実行で1件、次の全件実行で3件（failure 1・error 2）、`tests.test_server` 単体で7件中4件、**そして最後の全件実行では601件すべて OK**。 対象は `test_concurrent_reads_during_atomic_rewrites`・`test_api_state_index_and_404`・`test_api_reports_isolation_and_exclamation_instead_of_rejecting_them`・`test_concurrent_state_requests_share_one_rebuild` の4件で、すべて同じ原因である。件数が揺れるのは、同一プロセス内で前のテストがキャッシュを暖めているかどうかで冷える回数が変わり、冷えたときの所要（13〜15秒）が10秒の壁をどれだけ超えるかが実行時の負荷で動くためである。**壁のすぐ外側にいるので、通る回と落ちる回が生じる。**「flaky だから無関係」と片付けず、順に確かめた。

1. **単体でも落ちる**（12.1秒）。並列実行の干渉ではない。
2. **作業を退避したクリーンな main でも落ちる**（11.8秒）。私の変更が原因ではない。
3. **冷と暖を分けて実測した**。`serve_viewer._read_archive_payload_once()` は同一プロセス内の `_DERIVED_CACHE` が効くと **0.03秒**、冷えると **14.89秒**。テストの HTTP タイムアウトは **10.0秒**（`tests/test_server.py` L56）。落ちるのは冷えたときだけである。
4. **私の9行の寄与を、新鮮なプロセスで各3回測った**（キャッシュを持ち越さない条件）。

| 条件 | 実測（秒） | 中央値 |
|---|---|---|
| 私の行を含む | 13.96 / 13.81 / 14.62 | **13.96** |
| 退避したクリーン main | 14.32 / 13.02 / 15.69 | **14.32** |

**私の行を含む側がわずかに速い。** 差は測定雑音の範囲で、9行の寄与は検出できない。素材4,262件・CPU2コア・load 0.58–0.93 のこの環境では、冷えた payload 構築が常に10秒の壁の外側にいる。CI は main `5c2c3f57` で緑なので、CI の実行環境では内側にいる。

最初に私は「10.59秒なので今回壁を越えた」と書いた。**それは1回のサンプルで、間違いだった。** 冷暖を分けず、自分の行の有無も比べていなかった。6回測り直すと、壁を越えたのは今回の追加ではなく、この環境では既に越えていた。§9-1 の最初の版をここに訂正して残す。

**タイムアウトは引き上げなかった。** 二つの理由による。第一に、検査の閾値を緩めることは遅くなったという事実を隠す操作であり、それを実測と同一セッションで黙って行うべきではない（§6 でエンジンを書き換えなかったのと同じ理由）。第二に、これは検査の変更なので、`prompts/start.md` が台帳追記と同じ PR に入れるなと命じている変更である。**落ちたという事実だけを記録し、直すかどうかは次の判断に残す。** 次に読む者への手掛かり：冷えた構築が14秒、暖かい構築が0.03秒なので、支配的なのは構築そのものである。素材数に対して線形なのか shards の走査が支配的なのかは未測定で、`_ensure_derived`（L236–）が候補になる。
