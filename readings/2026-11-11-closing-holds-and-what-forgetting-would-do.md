## §3 利用者の問い——抽出して再登録し、古いデータを忘却するほうが自然か

問いは三つの操作を一つに束ねている。**分けると答えが変わる。**

| 操作 | 人間の記憶での名前 | この書庫で既にあるか | 実測 |
|---|---|---|---|
| 必要な情報だけ抽出して固定する | 固定（consolidation） | **ある**（`readings` → `claims`） | 11.1M 字 → **209,295 字（1.9%）** |
| 新しいルールで再登録する | 再固定化（reconsolidation） | 部分的（`supersedes`・`errata`） | 351行中11行 |
| 古いデータを忘却する | 忘却（削除／抑制） | **無い**（§5.3 で明示） | — |

### 3-1 「抽出して固定する」は既に走っている。98% は既に想起されない

`readings/*.md` は **11,098,747 字**。`claims` は **1,375件・209,295字**。**1.9%。**

つまり、**残りの 98.1% は、すでに「想起されない」状態にある。** 削除したわけではなく、固定されなかっただけである。人間の忘却も、多いのは痕跡の消去ではなく**検索手がかりの欠落による想起失敗**だとされる。この書庫は、その意味の忘却を**すでに実装している**——`claims` に抜き出せなかった報告は `return_status: "metaphor_unconnected"` として残り、想起の回路から外れる。

**だから「古いデータを忘却する」を追加しても、想起の量はほとんど減らない。** 減るのは 1.9% の側ではなく、まだ固定されていない 98.1% の側で、そこは今も想起されていない。

### 3-2 コンテキストは、台帳の大きさでは膨らんでいない（実測）

| 測ったこと | 2026-11-02（docs §6.1 の記録） | 2026-11-11（今回） |
|---|---:|---:|
| 報告 | 411本 | **688本（+67%）** |
| notes | 5行 | **351行（70倍）** |
| packet 全体 p50 | 34,223 B | **37,295 B（+9%）** |
| packet 全体 max（予算あり） | 49,042 B | **59,024 B（+20%）** |
| §3 予算なし p90 | 15,602 B | **17,483 B（+12%）** |

**台帳は桁で増え、1セッションが読む量は1割しか増えていない。** 二段構えの検索（L1 索引→L2/L3 本文）が効いている。**「データの過度な膨張によるコンテキスト崩壊」は、この設計では起きていない。** 起きるとすれば、台帳ではなく**索引**の側である（§3-4）。

### 3-3 「新しいルールで再登録する」は、いちばん危ない操作である

再固定化は、記憶が呼び出されて一時的に不安定になり、**そのときの文脈で書き換わる**過程である。利点（更新できる）と危険（歪む）が同じ機構から出る。

この書庫で、その危険が実証されている。**「綿花」**——要約にあった語が原典には0回で、その語を含む抽象化が報告に流れ込み、原典照合で初めて剥がれた（`NOTE-20261107-f42b8b`）。**要約を新ルールで再登録すると、この種の誤りを上書きではなく増幅する。** 今日の第九報告も同じ形の誤りだった（古びた保留を、原文に戻らず現在形として読んだ）。

**したがって「再登録」は、原典か台帳 ID に戻れる範囲でだけ行うのが安全である。** `scope` が「語を引用する、説明しない」と定めたのは、まさにこの理由だった。

### 3-4 圧力は「保存」ではなく「索引」にある

| 測ったこと | 値 |
|---|---:|
| `READING_MAP.md` 全体 | 1,123,470 B |
| うち §8 精読ノート索引（L0、「常に引ける」とされる層） | **172,273 B（701行）** |
| docs が記録した 411本時点の L0 | 102 KB |
| `map/`（git 管理外・再生成） | 14,397,458 B |
| §3 の予算で窓外になった素材 | 48問で 270件 |

**L0 は 411本で 102KB、688本で 172KB。+68%。** 「常に引ける」層が 172KB になったので、実際には毎回その一部しか読めない。ここが本当の成長点である。

§3 の窓外 270件は、**忘却を予算で代行している**状態だと言える——削除せず、載せない。docs §5.3 が「減衰をデータから削除せず表示だけに出す」と書いたのと同じ作法が、既に検索の側で動いている。

### 3-5 まとめ（比喩の測り直し）

- **「必要な情報だけ抽出して新ルールで登録」**——前半は自然で、既に走っている（1.9%）。後半（新ルールでの再登録）は、**原典に戻れる範囲でだけ**行うべきで、無条件には自然でない。
- **「古いデータを忘却する」**——**今は利益が測れない。** コンテキストは削除で減らない（p50 37KB）。想起されない 98.1% は既に想起されていない。減るのは監査の可能性だけである。
- **代わりに効くのは索引の圧縮**——L0 172KB、§3 窓外 270件。ここを「要約1行」へ寄せるのが、忘却の代わりに自然な操作である。族1・族2・族3 の dossier は、その実例（679報告 → 3族）として既にある。

## §4 判定（形式・外延・意味の自己申告）

- **形式**：§1 の数は `tools/held_report.py`、§2 は `git diff`、§3-2・3-4 は `--packet-stats`（シード `b14ce9f0`）と `wc -c`。再現できる。
- **外延**：§3-5 の結論は「削除では目的が達成されない」という**測った事実**に依拠する。だが「忘却が不要」とは言っていない。**想起の精度（precision）を上げたいなら、忘却に相当する操作は要る**——それを予算と索引圧縮で代行できる、というのが本稿の主張である。
- **意味**：人間の記憶の機構についての**経験的な主張は判定していない**。固定・再固定化・想起失敗という区別を、書庫の操作を分けるための比喩として使っただけである。脳科学の知見の正しさは、この書庫の主題ではない。

## §5 限界

1. **`held_report.py` は「触れた」しか見ない。** 同じ素材を読んだ後続が保留を閉じたかは、読まないと分からない。33件の候補は未読である。
2. **80件（ID の無い保留）は永久に照合できない。** 遡って ID を足すことは、追記専用では元の文の書き換えになるので行っていない。
3. **packet の比較は時系列で2点だけ**（2026-11-02 と今回）。しかも packet 全体はシード依存なので、別シード間では比べられない（`--packet-stats` の注意書きどおり）。
4. **`map/` は再生成物**なので、14.4MB という値は保存の圧力ではない。
5. **L0 172KB のうち、実際に各セッションが何割を読んでいるかは測っていない。**
