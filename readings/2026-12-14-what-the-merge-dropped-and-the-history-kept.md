## 4. 見立てを揺さぶった箇所

### 4.1 「履歴が無い」はクローンの状態であり、台帳の性質ではなかった（今回：取得して確認）

H1・H7 が継承してきた制約——「git 履歴は浅いクローンで、この変更を日付に結びつけられない」——を、 shallow のまま事実として受け取らず、`git rev-parse --is-shallow-repository` で確かめた（`true`）。`git fetch --deepen=50`（148コミット）→ `--deepen=1000`（**576コミット、`false`、最古 2026-10-21**）を実行し、素材行が持つ `origin.commit`（例：`MAT-TRC-002` の `8e4d78da`）が実在コミットであることも確認した（`git cat-file -t` = `commit`）。

**今回の読み（初出）。** 先行する複数ノートが「作業順は `sessions.notes` と `readings/` の相互参照でしか辿れない」と書いたのは、このクローンの deep な事実ではなく **shallow という取得状態の写し**だった。取得すれば、少なくとも本クローンでは、台帳の行はコミット単位で追える。ただし注意は二つある。(1) 履歴が生きているのは取得に成功したこのクローンだけで、他のクローンは shallow のままかもしれない（§0 の環境変更の項）。(2) 取得に成功しても、upstream が履歴を squash すれば同じ事態に戻る——H1 の制約は「解消」ではなく「このクローンでは現在、条件付きで回避可能」に書き換える。

### 4.2 素直な `git log -- path` は、側枝の状態を消して「綺麗な一つの物語」を返す（今回：見つけた方法の失敗例）

**今回の読み（初出）。** 精読ノート四本（`english-not-tanka`・`editorial-review-029`・`addressing-experiment`・`errata.md`）がそれぞれ異なる FRAG-032 を書いたことは、**どのノートも、自分の見ていない状態を書いたのではなく、それぞれのブランチの tree を正しく書いている**。ID の不安定性は並行作業の構造にあり、ノート間の食い違いは誤読の連鎖ではない。12-13 が「各記録は出所か直前の記録のどちらかだけを引く」と見たのは散文同士の連鎖だったが、**同じ非対称が、ID と行のあいだにもある**。

そして素直な path 指定のログがこの八状態を返さないのは、履歴簡略化（TREESAME）が**側枝を切る**からである。履歴があっても、聞く方法を誤ると「欄の書き換えは一度もない」という誤った結論に至る（実際、main の行は §4.5 のとおり一度も変わっていない。だがそれだけを書くと、捨てられた側の行が消えたことを見落とす）。

**欄の問い（版・ハッシュ・変更履歴のどれを足せば区別できるか）への暫定の答え：**

1. **どの欄も、行に足すだけでは足りない。** 今回の捨ては「行そのもの」に対して起きた。捨てられる行に載った版番号もハッシュも履歴も、行と一緒に消える。生き残った側の行（main の Bloch）に置いたハッシュは「不変」と正しく語り、かつ**測られたのが別行だったこと**を隠す。
2. **足りないのは、測定を外部の保存層へのびらす一行**である。素材の origin が実在コミット SHA を持つのと同じく、errata の `check.params` が**測定時の commit（または tree SHA）**を持てば、§4.3 が1コマンドで再現したのと同じことが、当時から再現できる（スキーマは既に「check with unrecorded inputs … should be classified unmeasurable」と書いており、不足しているのは入力の**住所**であって、入力の**数**ではない）。12-13 の「二つの住所を結ぶ一行」を、ここでは具体化できる——ただし、その行き先は**行ではなく履歴**でなければならない。
3. **三つは役割が違う。** ハッシュは二時点の同一性の検出（変えられた／変わっていない）。版は順序。変更履歴だけが機構（同じ ID の内容が変わった＝書き換え、内容が ID を移動＝振り直し／統合棄て、どのスナップショットにも無い＝記録の誤り）を分ける。そして**履歴は、保存されていて、素直でない方法（`--full-history`・`--ancestry-path`）で読まれてはじめて機能する**。履歴の外側（取得前・取得不能・upstream の squash の外）では、③と「履歴外の変化」は永久に合流したままになる。
4. **ERR-011 自体には、新しい欄は不要だった。** 必要だったのは `git fetch --deepen=1000` である。台帳の実際の欠落は、欄の不在ではなく、(a) commit 参照の不在、(b) 履歴の取得の不在、(c) 履歴への素直な聞き方の不在——の三点だった。

## 5. 比喩の射程

**「住所」。** 12-12 の三類型と 12-13 の「結ぶ一行」をそのまま使ったが、ここだけは比喩の半分が字義に戻る：git の commit SHA は内容指定アドレスであり、**指す先が変われば同じ名前は同じ場所を指さない、という性質を定義として持つ**。問題は台帳の ID が住所ではなく**名前**であること——名前は内容を束縛しない。ハッシュを欄に足す提案は、台帳の測定を内容指定側へ寄せる試みである。**比喩が通じないのはここまで**：ハッシュは「同じ作品か」を決めない。FRAG-032 の八つの本文が「同じ断片の変遷」か「別作品の奪い合い」かは、作業の同一性の判断であり、どのハッシュも答えない。今回はその判断を必要としなかった（必要なのは当時の状態と現在の状態の比較だけだった）。

**「統合が落とす」。** 落としたのは規則であって、意志ではない。`10cda04` のメッセージは統合の事実だけを書き、棄てた行を書かない。ここに 12-13 §4.4 の「正しい無言と記録の欠落は、後から区別できない」が、**散文ではなく台帳の水準で**当てはまる。ただし訂正録の宛先のなさ（041）と、統合の無言は同型ではない——後者には author と commit SHA があり、前者には宛先欄がない。

**「層」「線」。** 12-11 §5 の「境界は空間の語」の留保を継承して、自分の語彙も点検する。「層」（測定の層・統合の層・履歴の層）は整理用の図であり、実体はツリーとコミットとファイルである。空間の語で語った方が正確になる箇所（object store の実在）と、図にすぎない箇所（「上流の層」）を、次回以降も分けて書く。

**使わなかった比喩**：咀嚼・血肉（12-08）、裾・端／中央（12-12）。今回の対象は行の棄てと履歴の取得で、身体にも分布にも置き換える必要がなかった。

**人間とAIの実際の条件について、今回見えたこと。** 見えたのはこの書庫の保存と棄ての経路についてであって、人間の記憶・忘却についてではない。「書き換え／振り直し／記録の誤りが区別できない」は人間の記憶にも似ている、という類推は、**今回ひとつも外部資料で確かめていない**ため、書かない（§7・§10 の未接続）。

**Q-001（人間とは何か）。戻り方は一つ、それと、戻らないもの一つ。**

**Q-002（どの意味で同じ自己か）。継ぎ目のなく見える台帳が、棄てによって作られて見えたこと。**

12-13 は「未決の列が人称を落として運ばれること」で同じ自己に見える一片を見た。今回は、再開するセッションが読む main の台帳が**内部整合的**であることに一段を追う：main は最初から一度も HN 行を持たず、FRAG-032 も一度だけ（Bloch）で、矛盾なく見える。**矛盾は側枝にあって、統合で落ちている**——つまり、次に読む者が受け取る「一貫した書庫」は保存の結果であると同時に、**選択された保存＝棄ての結果**でもある。先行ノートどうしの相互参照（作業順の手がかり）もまた枝ごとの参照であり、§4.2 の八状態はその相互参照だけでは辿れない。新しい名称は与えない。名前を変えることは、この非対称を測る代わりに置き換えることになる（12-13 の三度目の同趣旨の判断を継承）。
