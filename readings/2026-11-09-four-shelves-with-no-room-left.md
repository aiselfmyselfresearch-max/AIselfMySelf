## §1 実測1——落ちるのは CI の size-budget ステップではなく、テストである

`tools/size_budget.py` の `--strict` は soft 超過を致命的にする（同ファイル 817行 `if args.strict and soft_exceeded: ... return 1`）。ファイル数次元も status に寄与する（`_status_for_pair` に `count, soft_shards, hard_shards` を渡している）。

しかし `.github/workflows/ci.yml` 32行が実行するのは **`python3 tools/size_budget.py`（`--strict` なし）** である。soft 超過は WARN で rc=0。つまりこの段階では CI は赤くならない。

赤くするのは**テスト**だった。`tests/test_size_budget.py:149` の `SizeBudgetTests.test_real_repository_is_within_strict_limits` は、**実リポジトリに対して `--strict` を実行し rc==0 を要求する**。`docs/parallel-work.md` §3 はこれを既に明記している（「CI の size-budget ステップ自体は非strictでも、後続の回帰テストがこの条件を検査する」）。

### 1-1 実験—— ordinary な1セッションを模して、rc を測った

リポジトリの複製を一時ディレクトリに作り（本物の台帳に触れない）、そこで二つの場合を比較した。

| 場合 | 作ったファイル | `size_budget.py --strict` |
|---|---:|---|
| 複製そのもの（`c7a6f55`） | 0 | **rc=0 / PASS** |
| 新しい実日付（2026-11-10）で sessions・read_log・notes に1本ずつ新シャード | 3 | **rc=1 / FAIL**（WARN 3件：`files: 96/95`・`90/89`・`91/90`） |
| 同じ3行を**既存シャードへ追記**（新ファイル0） | 0 | **rc=0 / PASS** |

資料を取得しないセッションでも、**3行書くだけで落ちる**。落ちてから直すのではない。書いた時点で落ちる。

### 1-2 複製実験の限界

三つ目の場合で `validate_seed.py` は `path references a missing file` を報告した。これは模した note 行が実在しない報告を指したためで、**実験の作り物の欠陥**であり、書庫の所見ではない。`--strict` の rc だけがこの実験の読み取る値である。

### 2-1 手順7（同日グループ全吸収）が成立する日付は、四つの棚にいくつあるか

手順7は「ある日付 `D` の**非統合シャードが全て**移動可能であるとき、和集合順を構成上まったく変えずに吸収できる」という条件つきの手順である。四つの棚について成立する日付を数えた。

| コレクション | 手順7が成立する日付数 | 内訳 | 既存のゼロ12桁シャード | **回収できる純減** |
|---|---:|---|---:|---:|
| `read_log.d` | 1 | 2026-11-09（1本） | 同日のものが**ある** | **−1** |
| `sessions.d` | 1 | 2026-11-09（2本） | 同日のものは**ない** | **−1** |
| `notes.d` | 1 | 2026-11-09（2本） | 同日のものは**ない** | **−1** |
| `materials.d` | 3 | 各日付1本ずつ | 該当日のものは**ない** | **0** |

`materials.d` が 0 である理由：手順7で回収できるのは「その日付の非統合シャードが1本だけで、かつ同日のゼロ12桁シャードが既に存在する」場合だけである。移動可能な3日付はいずれも1本ずつで、同日の受け皿が無い。**受け皿を新しく作れば、削除した1本と相殺して純減0**である。もう一方の方式（手順2の「連続した先頭範囲を先頭の既存ゼロ12桁シャードへ延長する」）も届かない——先頭側から連続して移動可能な範囲に、移動可能シャードが1本も無いからである。

**したがって `materials.d` には、認められた手順で回収できる枠が1つも無い。** 91/91 のままである。

### 2-2 `materials.d` にもう一つの出口はあるか

`state/materials.jsonl`（凍結ベース）は `tools/import_researchos.py --write` が再生成する唯一の例外で、**空でないシャードが `materials.d/` にある間は `--write` を拒否する**（§3 の表）。つまり全88本をベースへ戻せばディレクトリごと消えるが、そのためには88本全てが移動可能でなければならず、実際は6本である。**この出口も同じ理由で塞がっている。**

### 2-3 回収速度と生成速度

手順7が四つの棚から回収できる純減は合計 **3本**（read_log 1・sessions 1・notes 1・materials 0）で、しかもその対象は**すべて 2026-11-09 の、いちばん新しいシャード**である。§3 手順1は「実行中の他セッションのシャードは扱わず、**今回のセッションのシャードも選ばない**」と言う。回収できるのは前回以前のセッションのシャードだけで、**回収は生成に1セッション遅れる**。

一方、生成は1セッションあたり最大4本（materials・sessions・read_log・notes）。**回収速度（≤1本／コレクション／セッション、しかも1日遅れ）は生成速度（1本／コレクション／セッション）を上回れない。** 上限の履歴（31コミット中24回 SUM が動き、720→800→845）は、この不等式が実際にどう解決されてきたかの記録である——**統合ではなく、上限の引上げによって。**

## §3 実測3——前回私が使った逃げ道は、一般化しない

前回は新シャードを作らず、**同じ実日付の既存シャードへ追記した**。それで `--strict` は通り、マージも通った。この手順を「枠が0のときの標準的な逃げ道」として書いてよいだろうか。測ると、書けない。

### 3-1 「ファイル名順で末尾のシャードに追記する」は、日付を偽造する

追記先を選ぶ素朴な実装（`sorted(glob("*.jsonl"))[-1]`）を複製内で試した。三つのコレクションすべてで、選ばれたのは**内部編年で未来の日付を持つシャード**だった（2027-02-18、2027-02-21 のゼロ12桁シャード）。

§3 手順2は「**日付を偽造しない**：行の実日付と違う日付で新しい統合シャードを作らない」と定め、例として「作業日のゼロ12桁シャードに前日の行を入れる」ことを挙げている（原文の例は具体的なシャード名を含むが、**この報告では意図的に省いた**——省かないと、来歴の記述でもない引用が `readings/` の地の文からの参照として数えられ、§2 の 378 という数を将来のセッションが測るときに1件汚すからである）。文言は「新しい統合シャードを作らない」だが、**理由は「日付で順序を偽造する悪循環」**である。実日付 2026-11-10 の行を 2027-02-21 のシャードへ追記するのは、新しいファイルを作らないだけで、同じ偽造である。したがってこの実装は採用できない。

**正しい条件は「ファイル名の日付が、行の実日付と一致する既存シャード」である。** そして前回それが可能だったのは、**同じ実日付のシャードが偶然すでに存在したから**にすぎない。新しい実日付のセッションでは、一致するシャードは1本も無い。

### 3-2 `materials.d` では、一致するシャードを行の内容から特定できない

`materials.d` の2,731行を走査した。**`created_at`・`date_real`・`started_at`・`acquired_at` のいずれかを持つ行は 0行**。行の最上位欄は `material_id, kind, title, passage, passage_language, source, origin, verification, motif_ids, context, scope_note, source_note, literary_invitation` で、**日付を持つ欄が一つも無い**。

したがって `materials.d` では、シャードの**ファイル名の日付だけが**日付情報である。そして §3 手順1は「ファイル名の日付を実作業順とはみなさない」と言う。**実日付と一致するシャードを選ぶという条件が、`materials.d` では検証不能である。**

### 3-3 逃げ道の全体像

| 選択肢 | 新しい実日付のセッションで使えるか |
|---|---|
| 新シャードを作る | **不可**（§1-1 で rc=1 を実測） |
| 同じ実日付の既存シャードへ追記 | **不可**（一致するシャードが存在しない。前回使えたのは同日の先行シャードがあったから） |
| 別日付のシャードへ追記 | **不可**（§3-1、日付の偽造） |
| 統合して枠を作る | **materials は 0**（§2-1）。他3コレクションは各 −1 だが、対象は前セッションのシャードで、1日遅れ |
| 行を短くする | **不可**（追記専用、既存行は書き換えない） |
| そのコレクションに行を書かない | **可**（資料を取得しないセッションは materials 行を必要としない。しかし sessions・read_log・notes は通常のセッションで必須） |
| 上限を1だけ上げる | **可。しかし §3 が「既定にしない」と明記** |

**sessions・read_log・notes の三つについて、新しい実日付のセッションが認められた手順だけで書き切る経路は、統合を先に実行する場合に限られる。`materials.d` については、その経路も無い。**

## §4 実測4——恐れていた欠陥は無かった（そして私の最初の集計が間違っていた）

枠の問題を測る途中で、**和集合順が意味を持つか**を調べた。追記先を既存シャードに選ぶなら、行が和集合の中でどこに並ぶかが変わるからである。

`tools/note_index.py` は `rows[-1]` を使う（440行のコメントは `# later rows win`）。`order_note_rows`（359行）は台帳順を基底にし、明示的な `supersedes` だけで位相的に並べ替える。同関数の docstring は「内部編年の未来日付で書かれたシャードが、それを差し替える実日付シャードより後に並ぶことがある」と、**この危険を既に名指している**。

### 4-1 最初の集計——そしてその撤回

287 note 行のうち、同じ報告を指す行が2本以上ある道は **15**、そのうち明示的な `supersedes` を持つものは **8**、**和集合順だけに依存するものは 7** だった。

私はこの7道について「和集合順で勝った行が `created_at` の最新行と一致するか」を数え、**6件が不一致**と出した。これは `READING_MAP.md` が差し替え済みのノートを現在として表示している、という欠陥の候補に見えた。

**この6件は私の集計の誤りである。** `created_at` が**日付だけで時刻を持たない**行どうしを比較していたため、同着が起きた。同着を `max()` が先頭の索引で勝手に「最新」と決め、それを基準に不一致を数えていた。**判定基準そのものが同着を解決できないのに、解決されたものとして数えた。** 撤回する。

### 4-2 実日付（`date_real`）で判定し直した結果

`date_real` は287行すべてが実日付（2026-11-09 以下）で、未来日付は0行である。これで7道を判定し直した。

| 判定 | 件数 |
|---|---:|
| `date_real` が同着（**台帳はどちらが後かを判定できない**） | **5** |
| 和集合順の勝者が実日付の最新と一致 | 1 |
| 和集合順の勝者が実日付の最新と一致しない | 1 |

不一致の1件も欠陥ではなかった。勝者の行が `date_real` 欄を**持たない**場合で、`note_index.py` の統合は欄単位で「**行にその欄があれば**上書きする」ため、値を持つ先行行の `date_real` が生き残る。`READING_MAP.md` の該当行を確認して、表示が正しいことを確かめた。

**つまり恐れていた欠陥は存在しない。** 和集合順が実際に勝敗を決めるのは7道だけで、うち5道は**どの欄を使っても順序をつけられない同着**であり、残り2道は表示を誤らない。

### 4-3 残った所見——同着を解決しているのは、十六進の接尾辞である

欠陥は無かったが、測ったことは残る。

- **`created_at` の粒度**：287行のうち **281行（97.9%）が日付のみ**、時刻を持つのは **6行**。
- **`created_at` の時計**：**59行（20.6%）が未来日付**（内部編年）。`date_real` の未来日付は 0行。`created_at[:10] != date_real` は **130行（45.3%）**。
- したがって **`created_at` は実時間の鍵ではない**。実時間の鍵は `date_real` だけで、それは note 行にしか無い（sessions 行の欄は `session_id, started_at, human_direction, question_ids, context_material_ids, produced_fragment_ids, new_question_ids, prompt_template, notes, generator` で、`date_real` を持たない）。
- そして `sessions.started_at` は565行のうち **238行（42.1%）が未来日付**で、和集合順との pairwise 逆転は **34,616/159,330（21.7%）**。

**同じ実日に2本の note 行があるとき、どちらが勝つかを決めているのは、台帳のどの欄でもなく、シャードファイル名の十六進の接尾辞である。** 表示は誤らない（§4-2）ので欠陥ではないが、**規則のように見えるものが乱数で決まっている**。前回の報告 §5-1 で「私の連想はファイル名の辞書順から来ていることが測定できる」と書いたのと同じ形が、ここにもある。

処方は二つで、どちらも新しい道具を要しない：**`created_at` に時刻まで書く**（私の行は既に書いている）、**同じ道を指す note 行を書くときは `supersedes` を明示する**。後者は手順8に条件として入れた（§6）。

## §6 裁定——手順8を追加した（そして `editorial_decisions.d` には書かなかった）

### 6-1 追加した手順

`docs/parallel-work.md` §3「統合シャード（保守）」に**手順8**を追加した。内容は §1〜§5 の実測に一項ずつ対応する：

1. 書く前に `size_budget.py --strict` を実行し、**自分が行を書くコレクションの残り枠を見る**。
2. 枠が0なら、**ファイル名の日付が行の実日付と一致する既存シャードへ追記する**。条件は三つ：(a) オープンな PR がその経路に触れていない（`gh pr list --json files`）、(b) 既存行の著者セッションがすべてマージ済み、(c) 自分の行にシャード名を書かない。`notes.d` では加えて、**同じ道を指す行が既にあるなら `supersedes` を明示する**（§4-3）。
3. 一致するシャードが無い場合、**別日付のシャードへは追記しない**（§3-1）。手順7で枠を1つ作る（§2-1 の到達範囲：read_log・sessions・notes 各 −1、materials 0）。
4. 枠を作れない場合（現在の `materials.d`）に残るのは、**そのコレクションに行を書かない**か、**上限を1だけ上げる**かのどちらかで、後者は既定にしない（§3 追記2）。上げた場合は実測を添える。
5. **CI の size-budget ステップは非strictである。** 落ちるのは `tests/test_size_budget.py::SizeBudgetTests::test_real_repository_is_within_strict_limits` なので、`--strict` を自分で回さない限り見落とす。

### 6-2 なぜ `editorial_decisions.d` に裁定行を書かなかったか
