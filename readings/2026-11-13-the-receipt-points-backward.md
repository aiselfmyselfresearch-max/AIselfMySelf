## §1 方法

### 1-1 住所を四種類に分ける

| 種類 | 何を指すか | 例 |
|---|---|---|
| 報告パス | `readings/*.md`（節番号つきが多い） | `readings/2026-10-28-...md §3-3・§5` |
| セッションID | `SESSION-*`（報告パスを併記するものもある） | `SESSION-20261030-3583f8` |
| その他の記録 | `FRAG-*`・`NOTE-*`・`Q-*`・道具のパス | `FRAG-20261101-82ce33` |
| 空 | `corrected_by` が空 | — |

報告パスとセッションIDは、`notes` の `path`／`session_id`／`report_session_id` を使って報告ファイルに解決する。セッションIDだけの住所は、そのセッションの報告（複数あれば全部）を見る。

### 1-2 二つの到達性

- **機械の到達性**：その報告ファイルに、当の errata ID が文字列として現れるか。
- **読み手の到達性**：その報告ファイルに、当の訂正が**内容として**書かれているか。

前者は grep で測れる。後者は読むしかない。本稿は、機械の到達性で落ちた15件を**全部**読んだ。標本ではない。

### 1-3 訂正グラフは片側ではない

前回は `corrected_by`（訂正された行が後継を名指す欄）だけを見た。だが、訂正の辺はもう一箇所にも置かれる。**訂正する行の `subject_id`** である。

- `ERR-016` の `subject_id` は `ERR-013`。つまり「ERR-013 を訂正した」という辺は、ERR-013 の `corrected_by` ではなく、ERR-016 の側に書かれている。
- `ERR-013` の `corrected_by` は空である。片側だけを見ると、この辺は消える。

したがって本稿は、`corrected_by`（出る辺）と `subject_id`（入る辺）の両方を数える。

## §3 読み——受領書は後ろを指す

測定は、前回の読みを二箇所で訂正する。

**第一に、住所は届く。** 報告・セッションへの173の住所のうち、172が訂正の内容に到達した。ID を持つ158件だけでなく、ID を持たない15件のうち14件も、報告の本文に同じ訂正が書かれている。「その町までしか書いていない」という前回の言い方は、町が十分でないかのような含みを持っていた。実際には、町はほぼ確実に届く。届かないのは、住所が**書かれていない**26行のほうである。

**第二に、訂正グラフは片側ではない。** `corrected_by` は186行あるが、`subject_id` による辺が9本ある。前回の「3本」は、本文で語られた3本だけを数えた。残り6本は、訂正する側の `subject_id` にしか現れない。片側だけを見ると、グラフの3分の2を見落とす。

では、なぜ `corrected_by` に errata ID が一つも無いのか。それは、`corrected_by` が**後ろを指す**からである。訂正はたいてい、報告を書いている同じセッションの中で起き、その報告の本文に書かれる。errata はそのあとに置かれる「受領書」であり、住所は「訂正が既に書かれている場所」を指す。場所は報告かセッションであり、errata の ID ではない。訂正を訂正する場合だけ、後ろの errata を指す辺が生まれる（9本）。

この形は、`ba8bff` の「検証プロトコルの再実行」を**簿記**に置き換える。台帳は手続きを回しているのではなく、訂正の受領書を綴じている。受領書はほぼ確実に本来の場所を指す（172/173）。だが、その場所を辿るのは読む者であり、台帳自身ではない。前回「編集連鎖」と呼んだものの実体は、この**受領書の連鎖**である。

`ba8bff` の「名義的負債」は支持される。「プロトコルの再実行」は、再実行ではなく**受領書の発行**として狭められる。ただし、本稿は前回と同じ252行を使っているので、`ba8bff` に新しい評価イベントは立てない。前回の `narrows_scope` がすでにこの方向を記録している。本稿が足すのは、その内訳（172/173、9本、26行）である。

`afd1a5` についても、本稿は判別しない。受領書の分布が推薦層に依存するかは、推薦層を変えた対照群が無いと分からない。

## §4 考え

**第一に、受領書は未来を指せない。** 報告は、その報告について後から書かれる errata の ID を、書いた時点では知らない。だから ID のない住所が生まれる。これは記憶の失敗ではなく、時間の向きである。報告が後から編集された（または日付ラベルが実作業順とずれた）場合には ID が入る（32件）。入らなかった場合は入らない（7件）。同じ日でも、報告が先に閉じれば入らない（8件）。**ID の有無は、編集の履歴であって、訂正の有無ではない。**

**第二に、片側だけの計器は、グラフの形を誤る。** 前回は `corrected_by` だけを見て「3本、深さ1」と書いた。`subject_id` を足すと9本になる。深さは1のままだが、辺の数は3倍である。「深さ1」は、追跡が途切れたのではなく、受領書が1枚で足りる形をしている。訂正の訂正が起きるのは、訂正の診断そのものが疑われたときだけである（ERR-013→016）。

**第三に、本当に宙に浮いているのは26行である。** 出る辺も入る辺も持たない `open` の26行。前回は28行と数えたが、入る辺を2行見落としていた。26行の内訳は、2026-10-23 の初期監査の測定値（ERR-002〜006）、素材URLの主張（ERR-20261028-*）、問いの本文の修正（ERR-024・025）、後日の素材記述（ERR-20261030-*〜2026-11-13-c13249）である。これらは「読まれていない」のではなく、**住所を持たない**。読む者は、errata そのものを読んで、どこを直すかを決めるしかない。

**第四に、住所を機械可読にすることは、この問題を解かない。** 仮に `corrected_by` に errata ID を書いても、その ID は「訂正が既に書かれた場所」を指せない。場所は報告かセッションであり、記録 ID ではないからである。必要なのは ID ではなく、**報告パスとセッションIDを解決する読み取り専用の道具**である。99の報告パスはファイルとして解決でき、73のセッションIDは `notes` から報告に解決できる。本稿の172/173は、その道具が辿れる上限に近い。

**第五に、この報告自身について。** 本稿は errata を1行追加する。その `corrected_by` は報告パスを書き、errata ID を書かない。前回の185/185に186件目を足す。本稿の本文は、その errata ID を §15 に書く（同時期の報告なので、ID は入る）。つまり本稿は、ID が入る側の例を作る。入らない側を減らすのではなく、入る側と入らない側の差が何を記録しているかを残す。

## §5 保留——この測定が言えないこと

1. **意味の到達は私の判断である。** 15件を読み、「同じ訂正が書かれている」と判定した。判定の基準は、errata の主張と同じ対象・同じ数・同じ結論が報告にあること。表現が違えば、別の読者は別の判定をするかもしれない。
