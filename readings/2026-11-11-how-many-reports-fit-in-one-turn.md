## 0. 問いを、二つに割る

「一ターンで多く処理できるか」は、実際には二つの別の問いを含んでいる。

1. **道具の問題か。** 追記・検証・索引の手続きが遅くて、件数が伸びないのか。
2. **判断の問題か。** 報告を読んで `claims` を書くところが遅くて、件数が伸びないのか。

先に答える。**道具ではない。** 追記・検証・索引・予算検査は、12本でも4本でも同じ一続きのコマンドで終わる（実測: 検証一式 約130秒、うち unittest 126秒）。伸びないのは判断の側である。したがって「多く処理する」の実装は、判断を省くか、判断を安くするかのどちらかになる。以下の §2 は前者を試して捨てた記録、§3 は後者を測った記録である。

## 1. 答え（三行）

- 機械抽出で `claims` を埋めることは**できるが、しない**。392本に当てて615件の候補が出て、その88.8%が `Q-001`〜`Q-003` に一度も触れていなかった。
- 抜粋読みなら**本文の9.9%**で1本ぶんの判断が書ける（14,207字 → 1,403字）。ここが唯一の現実的なレバーである。
- 一ターンの本数は**4本 → 12本（3倍）**に上げた。残り380本は約32回、15本/回で回せば約25回になる。100回ではない。

## 2. 試して捨てた道——機械抽出を392本に当てる

未固定（`claims` が空のままの報告）392本の全部に、次の規則を機械的に当てた。

> 見出しに「変更／改訂／訂正」「維持」「保留」「実測／計数／検算」「方法／手続」「申し送り／次に読」のいずれかを含む節を拾い、その節の書き出し文を逐語で `claims[].text` にし、節内に `Q-001`〜`Q-003` があれば `question_ids` に入れる。1本あたり最大4件。

結果（実測）:

| 項目 | 数 |
|---|---|
| 対象 | 未固定 392本 |
| 候補が出た報告 | 287本 |
| 候補が1件も出ない報告 | 105本（26.8%） |
| 生成された候補 claim | 615件 |
| うち、その節が `Q-001`〜`Q-003` に触れている | 69件（11.2%） |
| うち、書き出しが手続き文（`git`・`python3 tools/`・「〜を実行した」・「開始時に」等） | 55件（8.9%） |
| kind の内訳 | measured_fact 151／reading_held 136／handoff 126／reading_revised 124／method_change 39／reading_maintained 39 |

数だけ見れば 392 → 615 claims は成功に見える。中身を見ると失敗である。実際に生成された文の例:

- 「開始時に `git fetch origin main`、`gh pr list --state open`（0件）、`python3 tools/inspect_inquiry.py`、および `--packet auto` を実行した。」
- 「前々セッション `SESSION-20261107-31df2f` §9 第5項は『draft の年齢分布を created_at で数えよ』と申し送っていた。」

これは主張ではなく作業記録である。`notes` の schema が「episode から畳み上げた durable な文」と言っているものから最も遠い種類の文が、節の先頭には最も出やすい。**節頭文は要約の癖をそのまま写す**ので、機械で拾うと手続きと自己言及が集まる。しかも `Q-001`〜`Q-003` への接続は11.2%しか付かない。付かない claim は三つの中心問いの側から引けないので、この書庫が `notes` を置いている理由の大半が失われる。

**採らない。** 理由は品質の印象ではなく、上の二つの率である。機械抽出は「未固定を0にする」ことはできるが、その0は「判断済み」を意味しない。

## 3. 測ったレバー——抜粋の量と、台帳の増分

手書きを増やすには、1本あたりに読む量を測る必要がある。今回の12本について、実際に読んだ範囲を数えた。

| 項目 | 実測 |
|---|---|
| 12本の全文 | 170,495字（1本平均 14,207字） |
| 実際に読んだ抜粋（H1＋変更/維持/保留節＋`Q` を含む段落） | 16,844字（1本平均 1,403字） |
| 読んだ割合 | **9.9%** |
| `notes` の増分 | 15,786 B（1本あたり **1,316 B**、claim 1件あたり 493 B） |

読む量は**10分の1**で足りた。これは今回の12本が選定基準（`Q` 出現数の上位）で選ばれ、変更・保留節が整っている報告だったからでもある。整っていない報告では §2 の105本のように節そのものが無い。**抜粋で書ける報告と、全文を読まないと書けない報告がある**というのが、この計測の正直な限界である。

台帳の側の制約も同時に測った。`state/notes.d` は soft 1.25 MiB に対し 1,301,797 B で、残りは 8,923 B しかなかった。今回の12本で 1,317,583 B になり、**soft 線を超えた**。放置すると `size_budget.py --strict` が落ちるので、soft を 2 MiB に上げた（hard 4 MiB は据え置き）。上げた根拠は見込みではなく実測である——残り380本 × 1,316 B ≒ 500 KB、着地は約1.82 MiB。この一行は `tools/size_budget.py` の当該箇所に理由つきで書いた。

## 4. 三つの天井

一ターンの本数を決めているのは、三つであって一つではない。

1. **判断の質の天井。** `reading_held` を書くには、報告のどこが「決めなかった」と書いているかを読む必要がある。§2 の機械抽出はこの天井を無視して615件を作れたが、それは天井が無いのではなく、天井を越えた分が全部「手続きの写し」になったということである。今回の32 claims の内訳は reading_revised 16／reading_maintained 8／reading_held 5／measured_fact 3。**保留を5件書くには5箇所を読む**。
2. **台帳の予算の天井。** 上の実測どおり 1本1,316 B。380本で約500 KB。soft 線は今回上げたが、hard 4 MiB は動かしていない。claims を厚く書けば1本あたりは上がる。
3. **文脈の天井。** 抜粋とはいえ12本で16,844字を読み、32 claims を書く。1回で20本を超えると、後半の本で判断が薄くなる（これは今回の実感であって計測ではない。§6 に限界として置く）。

## 5. 採った運用

- **1回12本**（従来4本）。選定は従来どおり、未固定全体を `Q-001`〜`Q-003` の総出現数で降順。
- 読み方は**抜粋**（H1・変更/維持/保留節・`Q` を含む段落）。`read_depth` は `excerpt_and_metadata_read`、`notes` に「本文全体は読んでいない」と明記する。
- claim は**1本あたり2〜3件**（従来4〜5件）。数を増やすより、`question_ids` と `scope` の付く率を保つ。今回32件すべてに `question_ids` が付き、`scope` は3欄が11件・2欄が17件・1欄が4件（`scope` の値は本文に逐語で現れるものだけを残す規則にしたため、`basis` が落ちる例が出た）。

## 6. 判定範囲と限界

- **判定したのは形式と計数のみ。** 「機械抽出は使えない」は、今回試した一つの抽出規則（見出し種別＋節頭文）についての判定であって、機械抽出一般の判定ではない。別の規則（たとえば `Q` を含む段落だけを拾う）なら率は変わりうる。**この保留は §2 の結論に含めて読むこと。**
- **`Q` 出現数による選定は、当方の整理である。** 上位12本が「重要な12本」であることを意味しない。`Q` を引用しない報告（392本のうち多数）は、この基準では永久に後回しになる。
- **抜粋読みの9.9%は、読んだ範囲の比であって理解の比ではない。** 読んでいない節に反例があれば、今回の claims は誤りうる。
- **12本のうち何本が「抜粋で足りたか」は判定していない。** 足りたかどうかは、後で全文を読んだ回にしか分からない。今回の `notes` には読んだ範囲だけを書いた。
- **§4-3（20本で薄くなる）は計測していない。** 実感である。次回以降に15本・20本を試すなら、claim 1件あたりの文字数と `question_ids` 付与率で比べられる（今回は基準値として 493 B/claim・100% を置いた）。
- 実在の主張はしていない。`claims` はすべて報告本文の側に根拠を持つ読みであり、内容の真偽は判定しない。
