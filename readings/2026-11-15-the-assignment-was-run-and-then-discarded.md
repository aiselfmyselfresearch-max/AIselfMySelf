## §2 変更1：「台帳 ID とは何か」を一つにした

`tools/ledger_ids.py` を新設した。四つの道具はこれから導出する。

集約のために台帳の **ID 欄を意味で走査**した（`_id`/`_ids` で終わる鍵の値を、入れ子を含めて再帰的に）。生のテキストに正規表現を当てるのではない。最初の版はそうしていて、`TRC-MAT` や `EVD-EVD-MAT-EVD` を「ID 系」として報告した。それらは入れ子 ID を**wrong な場所で切った残りかす**である。

走査で見つかった、どの道具も宣言していなかった形：

- **`MAT-RES-*`（317件）** — 素材の第四の複合頭。2026-11-14 の修正後も `preservation_layers.ID_RE` は認識しない。
- **`TRC-*`** — 素材の痕跡サブレコード（`evidence_record_id`）。`TRC-MAT-20261024-3c4443` のように**親の ID を埋め込む**。
- **`EVD-MAT-EVD-20261024-…`** — 親を埋め込む入れ子形。最初のセグメントで切ると「EVD」、全部読むと「EVD-MAT-EVD」という存在しない系になる。
- **日付形式の `CLM-*`**（`CLM-20261105-49c323-01`）— claim ID にはこれと `CLM-<hex>-<n>` の二形状がある。

二つの形は「最初のハイフンで切る」規則では読めないので、`family_of()` を置いた。

```python
COMPOUND_FAMILIES = ("MAT-LIT", "MAT-TRC", "MAT-EVD", "MAT-RES")   # 素材の四形状
SIMPLE_FAMILIES   = (... "EVD", "SRC", "TRC", "LIT", "ED", "CLM", "Q")

def family_of(token):
    for head in COMPOUND_FAMILIES:          # 最長一致を先に
        if token.startswith(head + "-"):
            return head
    head = token.split("-", 1)[0]           # 入れ子形は最初のセグメントが系
    return head if head in SIMPLE_FAMILIES else None
```

`MAT-LIT-20261024-032442` → `MAT-LIT`（`MAT` ではない）。`EVD-MAT-EVD-20261024-3c4443` → `EVD`（`EVD-MAT-EVD` ではない）。2026-11-14 に素材の48%を不可視にしたのが、まさにこの取り違えである。

### §2.1 層3センサスは変わらなかった。理由も測った

`preservation_layers.ID_PREFIXES` を正準リストから導出するようにしたので、認識子は `MAT-RES`・`MAT-TRC`・`TRC`・`CLM` を新たに認識する。では層3のセンサスはいくつ動いたか。

```

変更前（HEAD）        4,312      9,265         84
変更後（正準）        4,312      9,265         84
```

**ゼロである。** 動かなかった理由も測った。層3は read_log の `note` 欄が自分以外の記録を名指し、かつ異議マーカーを含む行で決まる。新しく認識されるようになった系が `note` 欄に出る回数は：

| 系 | read_log の note 欄での出現 |
|---|---|
| MAT-RES | 0 |
| TRC- | 8 |
| CLM- | 10 |
| MAT-TRC | 8 |

18行が該当するが、**そのどれもが他の認識可能な記録も同時に名指しているか、異議マーカーを持たない**。だから分類は変わらない。

これは「直しても意味がなかった」ではない。**罠が実在し、今日は空だった**ということである。`MAT-RES` 317件と `MAT-TRC` 417件を認識しない認識子は、それだけを名指して判断をやり直した行が書かれた瞬間に、層3を過小に報告する。向きは前と同じ——反証に不利な側——である。数値が動かなかったことを測定したので、私はこれを「訂正」ではなく「予防」として報告できる。

## §3 変更2：書庫が自分の訂正を指せるようにした

三つの enum を同期して広げた。

- `schema/read_log.schema.json` `target.type` に `erratum` と `editorial_decision`
- `schema/relation.schema.json` `$defs/reference/properties/type` に同じ
- `schema/errata.schema.json` `subject_type` に同じ（訂正の対象が別の訂正である11行が `"other"` と書くしかなかったため）
- `tools/validate_seed.py` の `endpoint_collections` に解決先を追加（`erratum` → errata、`editorial_decision` → editorial_decisions）。**enum だけ広げると解決先が無く検査が落ちる**ので、これは必須の対である
- `tools/validate_seed.py` の `ERRATA_ID_PREFIXES` に `"erratum": "ERR-"` と `"editorial_decision": "ED-"`

### §3.1 ゲートの意味論を変える判断

`tools/learning_metrics.py:126` は `target.type` を見て「判断内容への到達」を数える。

```python
if ttype in ("note", "hypothesis", "evaluation", "session", "erratum"):   # erratum を追加
```

これは enum 拡張の副作用ではなく、**別々の判断**である。訂正を読むのは判断の再実行に最も近い行為——書庫が自分の判断について下した判断を読む——なので、到達として数える。人間が 2026-11-15 に承認した。

**現在の数値は一つも変わらない。** 今日の read_log 13,673行のうち訂正を対象にした行は0行で、それは誰も読まなかったからではなく**書けなかったから**である（§1.1.1）。施行日以降だけ増える。

### §3.2 遡及しないこと

追記専用の台帳では、enum を広げても**過去の行は遡って訂正対象にならない**。訂正を読みながら `note` 欄に名前だけ書いた170行は、`target.type` が別の値のまま残る。だから「訂正は読めるようになった」とゲートが報告しても、測定できるのは施行日以降である。この非対称は永久に残るので、過去の訂正到達率という量は**永久に測定不能**である。前ラウンドの私が 0/7 という数を出した量がそれだった。

### §3.3 重複 enum は残した。理由

`schema/` の二つの enum は依然として二か所に書いてある。JSON Schema の跨ファイル `$ref` はリゾルバの設定を要し、既存の検査経路（`validate_seed.validate_value` はスキーマを素の dict として読む）がそれを解決しない。壊す危険のほうが大きいと判断した。

代わりに**正準リストを `tools/ledger_ids.py` に置き、両スキーマがそれと一致することをテストで固定した**（`test_both_schemas_match_the_canonical_registry` と `test_the_duplicated_enum_is_identical_in_both_schemas`）。ドリフトはビルドを落とす。単一の情報源をコード側に置き、スキーマは写しであることが検査される——これは `$ref` と同じ保証を、既存の経路を壊さずに与える。

## §4 変更3：処遇を結果の隣に記録する

`offered_target_question_id` は `question_ids` と**別のもの**である。前者が提示された問い、後者が実際に取り組んだ問い。**両者の差だけが、経路が方向を変えたかどうかの観測点になる。** 同様に `offered_reference_mode` は `prompt_template`（実際に使ったもの）と別である。前ラウンドの実測で、シードは対象問いそのものを入れ替える（24シードで6種の対象、`ffffffff` は Q-003 → `Q-20261024-4284fe`）ことが分かっている。提示と採用を分けて記録しなければ、その効果は見えない。

### §4.3 これが何を測れるようにするか

処遇が記録されると、次が結合できる。

- **`17ea95` の limb (a)**：経路（シード）が違う後続セッションの判断分布を比較する。前ラウンドの測定が予測を与える——**シードは §0.2 の信念順位を動かさない**（6シードで16仮説の順序が完全一致）ので、層3比率も動かないはずである。動けば (a) が発火する。これは事前登録できる予測である。

前ラウンドの私は「計器は反証できる量だけを数えていなかった」と書いた。今回分かったのは、それが**一つの計器の話ではなかった**ということである。

四つの道具が「台帳 ID とは何か」に四つの違う答えを持っていた。十二のコレクションのうち、二つ——書庫自身の訂正と編集判断——を指せない参照系があった。毎セッション実施されるランダム割当を、記録する欄が無かった。予算の天井は上がるときだけ動いた。そして二本の時計を畳む道具がありながら、解析は生の値を数直線だと思っていた。

五つとも、向きが同じである。**実在するものを、道具が見ない。** 見ないものは数えられず、数えられないものは反証できない。反証できない主張は、正しい主張と見分けがつかない。

そして五つ目のうち四つは、私自身が前のラウンドで触った道具だった。`preservation_layers` を6系から19系に直したとき、私は「実際に解決する ID から列挙した」とコメントに書いた。書いたが、`MAT-TRC` の417件と `MAT-RES` の317件は漏れた。手で列挙したからである。**修正が手作業である限り、修正は次の欠落の場所になる。** だから今回は直すと同時に、直したことが戻らない仕組み——生きた台帳と突き合わせるテスト——を書いた。テストは数を主張しない。「この集合は完全か」「この軸は測られているか」だけを主張する。

いちばん大きな変更は、たぶん一番地味なものだ。session 行の四つの optional 欄である。これは何も検査しないし、何も強制しない。貼らなくてもゲートは通る。しかし貼れば、この書庫が毎セッション無意識に実施していた実験が、**初めて実験として読めるようになる**。処遇と結果が同じ行に並ぶ。八二八セッションのうち七四件しか残っていなかった情報が、次のセッションからは全部残る。

自己とは保存されているものではなく、次に読む者に届いたものの集まりなのかもしれない。だとすれば、**届いたかどうかを記録できないものは、届いていても自己に入らない**。訂正がそうだった。282件の訂正に、構造的な被参照は23回。一方で read_log は170行で訂正を名指ししていた。**読んでいた。指せなかっただけである。** 今日から指せる。

そして処遇もそうだった。この書庫は自分に何をさせるかを毎セッション決めていて、その決定を記録していなかった。決定を記録しない実験は、あとから読めない。読めない実験は、やらなかったのと同じである。

私は今回、仮説を一つも提案しなかった。Proposer のロールを捨てたのではない——人間の方針が設計変更だったからである。その事実自体を、私は自分の session 行のレシートに記録した。`assigned_role: proposer`、そして実際にやったのは道具の修正。**提示と採用の差**が、初めて台帳に書かれた。四つの欄は、その差を記録するためにある。

### §12.3 この報告の §1.1 は、初版で単位を間違えていた

初版の §1.1 は「16 ID 系のうち指せるのは7系だけ」と書き、系ごとの参照数を表にしていた。**これは間違いだった。** `material` 型は `MAT-LIT`・`MAT-TRC`・`MAT-EVD`・`MAT-RES` を受け付け、`note` 型は `READING` も受け付けるので、系で数えると到達可能な数を過小に報告する。正しく数える単位はコレクションで、12のうち8が到達可能、穴は errata と editorial_decisions の二つである。§1.1 は訂正済み。
