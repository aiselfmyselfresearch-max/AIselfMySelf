# 記憶のアーキテクチャ — 人間のアナロジーでこの書庫の置き場を点検する

`docs/map-architecture.md` が「**増え続ける本文をどこに置くか**」（4層・レンジ分割・生成物は git の外）を定めたのに対し、本文書は「**増え続ける記憶を、次のセッションがどう取り出すか**」を定める。2026-11-02 の人間からの委任（「レポート群の扱いと、長期記憶／短期記憶・連想の設計を提案し、提案どおり実装せよ」）に応じて書き、同日に実装した内容を実測値とともに記録する。

## 1. 対応表 — 人間の記憶の階層と、この書庫の置き場

人間のアナロジーは**比喩**であり、このリポジトリの AI に記憶の主体があるという主張ではない（`CONTENT_POLICY.md`）。比喩として使う価値は、**「どの層が欠けているか」を名指せる**ことにある。

| 人間の記憶 | 機能 | この書庫の対応物 | 実測（2026-11-02） | 状態 |
|---|---|---|---|---|
| 感覚記憶 | 数百ミリ秒、未処理の入力全部 | 1ターンの生入力（委任文＋checkout） | — | 問題なし |
| **作業記憶** | 数秒〜数分、容量 4±1 チャンク | `inspect_inquiry.py --packet auto` の出力 | p50 34,223 B／max 49,042 B（既定・シード `9a7bda3c`）。**packet 全体はシード依存、§3 は非依存**（§6.1）。§3 に 16,384 B の予算 | **§3 のみ予算を実装**（§6.1・§7.5）。L0/L1/L2 の段階的読み込みは未実装 |
| **短期記憶** | 固定される前の、当座の保持 | 今回の `state/*.d/<branch-seed>.jsonl` シャード＋執筆中の `readings/` ノート | 9 コレクション＋notes で 10 | シャード境界が暗黙（§6.2） |
| **エピソード記憶** | 「いつ・どこで・何が起きたか」の語り | `readings/*.md` 411本、`sessions` 377、`read_log` 8,226、`errata` 121、`editorial_decisions` 123、`notes` 6 | 15.1 MB / 668万字 | 索引がなかった（§3、2026-11-02 実装）。判断の台帳化は **6/411 本**（§7.4・§7.5） |
| **意味記憶** | 事実・概念・関係（出典を失った知識） | `motifs` 59、`questions` 408 の DAG、`materials` 2,656、`taxonomy/shards` 1,553行 | 台帳 2.0 MB | 固定が一過性で凍結（§5.2） |
| **手続き記憶** | 「やり方」＝体の化した手順 | `prompts/` 10本、`tools/` 78本、`schema/` 10種、`docs/`、CI | 1.17 MB | 強い。ただし自己循環（§7.3） |
| 忘却・抑制 | ノイズを落とす能動的な過程 | `paused`、`errata`、`supersedes`、削除の禁止 | `paused` 24件・訂正 121件 | **減衰がない**（§5.3） |
| **連想** | 一緒に発火したものが繋がる | `relations` 5,997 本（8種）＋ `read_log` の共起 | 共起 2,624 対のうち**架橋 331 対（12.6%）** | 計測手段がなかった（§5、2026-11-02 実装） |

**この表から出てくる診断**：この書庫は意味記憶と手続き記憶が異常に強く、エピソード記憶の**量**も十分あるのに、エピソードの**検索路**だけが欠けていた。人間の記憶で言えば「日記は400冊あるが目次と索引カードが1枚もない」状態である。

## 2. なぜ `readings/` だけが索引の外にあったのか（実測）

`docs/map-architecture.md` の4層はすべて `state/` を指しており、`readings/` はどの層にも属していなかった。

| 索引 | `readings/` の収録 |
|---|---|
| `READING_MAP.md`（Tier 2） | **0 件**（実装前の grep 実測） |
| `map/`（Tier 3）＋ `manifest.json` | **0 件** |
| `read_log`（読み痕跡） | **0 件** — `target.type` の enum が `question｜motif｜material｜fragment｜session` の5種で、ノートを指せなかった |
| `schema/session.schema.json` | 報告パスの欄が**存在しない**（`additionalProperties: false`） |
| `README.md` §1・§2 の詳細窓 | 6 本（ローテーションで常に最新の3＋5件だけ） |
| `docs/sessions.md` 報告注釈目録 | 182 本 |
| `taxonomy/shards/*.jsonl` | 257 本（63%）— 2026-10-29 の16ユニット並列分類で**凍結**、以後の150本は未分類 |

到達可能性を実測すると（`tools/note_index.py`、markdown リンクと本文中のパス言及の両方を数える）：

```
readings/ 411 ファイル（.md 409 ＋ .tsv 1 ＋ .json 1）／ 15,100,787 B ／ 6,680,326 字
├─ どこかの文書からリンクされている        339 本
├─ パスが本文中に書かれているだけ            30 本
├─ 到達可能（和集合）                        369 本（89.8%）
└─ どの文書からも到達できない                 42 本（10.2%）  ← ls と grep と Git 履歴だけ
```

リンクは**出現した形のままで数えてはいけない**。この書庫には4種類の書き方が混在しており、`readings/` という接頭辞の有無だけで判定すると、報告どうしの相互リンク（`[前](2026-11-01-x.md)`）と `taxonomy/notes/*.md` の絶対 GitHub URL（`…/blob/main/readings/x.md`）をすべて取りこぼす。`tools/note_index.py` は各リンクを**その文書の位置から解決**して `readings/` に着地するものだけを数える（実装は `_normalise_link`、回帰テストは `tests/test_note_index.py::ReachabilityTests`）。生成物である `READING_MAP.md` 自身は到達元に数えない（§8 が自分自身を根拠にする循環を避けるため）。**同じ理由で、報告が自分のパスを引用したものも到達元に数えない**——`mv readings/x.md /tmp/` のような復旧手順を書く報告が自分自身を「到達可能」にしてしまい、測るべき孤立が減ってしまうためである。この除外は 2026-11-02 に入れた（§7.5）。上の数字は除外後のもの。

**2026-11-05 の追記。** この節が記録した「二つの時計」は、`tools/date_axis.py` と [`time-axis.md`](time-axis.md) で一本の軸に畳まれた。過去のラベルは書き換えず、新しい ID・シャードは実日付で採番し、軸は `sessions.notes`／`notes.date_real`／（未来でない）`started_at` から実日付を復元する。上の実測値は当時のまま残す（当時の値を今の値に書き換えない）。

さらに、**ファイル名の日付は作業順ではない**。名前についている日付は内部編年ラベルで、実行環境の実日付とずれる（例：`2026-12-31-the-hand-that-pairs-does-not-hold-the-child.md` の実日付は `2026-10-30`）。実日付を本文中に書いてあるノートは **206 / 411 本（50.1%）** で、残り半数は実日付を機械的に復元できない。

→ 帰結：エピソード記憶は「新しい順に並べる」ことも「古さで減衰させる」こともできなかった。**時系列という軸自体が、この書庫には二つあって、どちらも信用できない。**

## 3. データモデルの決定 — 三案の比較

人間からの問いは「レポート群を JSON で構造化し、それを管理する JSONL を作るのか／単一 JSONL か／ドメイン毎の階層 JSONL 群か」だった。結論から言うと **案2（単一コレクション＋挿入順シャード）を正本とし、ドメイン別の視点は生成索引として派生させる**。

### 案1 — レポート毎の JSON ＋ 管理 JSONL　**却下**

| 観点 | 判定 |
|---|---|
| 正本の数 | **本文が .md と .json で二重化**する。二つの正本は必ずずれ、どちらを直すかという新しい編集判断が毎ターン発生する |
| 追記専用原則 | 壊す。JSON は「更新したくなる」形式で、`state/*.d/` の思想（既存行を書き換えない）と相性が悪い |
| 予算 | `readings/` の 15 MB に構造化コピーが上乗せされ、`size_budget` の soft を即座に超える |
| 利点 | 本文を機械可読にできる |

**利点は正しいが、対象が間違っている。** 構造化すべきは本文ではなく、**本文から導出できる事実**と**読者が表明する判断**の二つである。前者は毎回読み直せばよく（保存すると必ずずれる）、後者だけが台帳に値する。これが §4 の分離原則になる。

### 案2 — 単一 JSONL（＝ `state/notes.jsonl` ＋ `state/notes.d/`）　**採用**

既存9コレクションと完全に同型。追加で得るもの：

- `validate_seed.py` のスキーマ検証・FK 検査・`supersedes` の非循環検査がそのまま効く
- `new_id.py NOTE` / `new_ledger_shard.py notes --create` がそのまま効く（並列安全な採番）
- `read_log.target.type: "note"` と `relations` の端点として**引用できる**ようになる
- `map_build.py` が索引を生成し、CI の `--check-map` が陳腐化を検出する

「単一ファイルに全成長を吸収させない」というこの書庫の衛生規則は、**単一コレクション**を禁じていない。禁じているのは単一**ファイル**であり、その解決はすでに `base ＋ 挿入順シャード` として存在する。`READING_MAP.md` 37 MB 事故の教訓は「コレクションを分けろ」ではなく「**正本と生成物を分けろ**」だった。

### 案3 — ドメイン毎の階層 JSONL 群　**却下**

| 観点 | 判定 |
|---|---|
| シャードキーの安定性 | `docs/map-architecture.md` §2.2 は「変わりうる値をキーにするとデータ移動が発生する」と明記している。**ドメイン（象限・モチーフ）は再読で変わる**値そのものなので、キーにすると再分類のたびにファイル移動＝履歴の書き換えが起きる |
| 並列書き込み | 同一ドメインのファイルを2ブランチが触れば衝突する。`docs/parallel-work.md` の4原則に反する |
| 探索コスト | 「Q-099 に触れたノート」を引くのに全ドメインを開く必要があり、索引として劣る。実際 `taxonomy/shards/` は16ユニットに分割された結果、1ユニットを読むだけでは横断的な引き当てができない |
| 利点 | ドメイン別の見通しがよい |

**利点は生成物として実現する。** 正本は挿入順シャード（安定・不変・追記専用）に置き、象限別・モード別・到達性別の**視点は `map/` に毎回生成**する。視点は増えても正本は増えない。

## 4. 分離原則 — 一つの事実に一つの正本

今回の実装の中核は、コレクションの新設そのものではなく、この分割である。

| 事実の種類 | 例 | 正本 | 理由 |
|---|---|---|---|
| **導出事実** | バイト数、字数、H1 の題、参照している台帳 ID、見出し列、ここへリンクする文書、`prompts/` から導かれるモード | `readings/*.md` 自身。`tools/note_index.py` が**毎回読み直す** | 本文から計算できるものを台帳に写すと、写した瞬間から古くなり始める。写しを持たないことが唯一の同期保証 |
| **判断** | モードの確定、象限、`return_status`、`read_depth`、固定された主張（claims）、顕著性、記録理由 | `state/notes.jsonl` ＋ `state/notes.d/`（追記専用・overlay） | 計算できない。誰かが読み、表明し、後の読みが上書き（追記）するしかない |

overlay の作法は `editorial_decisions` と同じ：**同じ `path` について後の行が前の行に勝ち、前の行は消さない**。内部編年ラベルが実日付より後へソートされる事故（`ledger_io._order_editorial_decisions` が処理しているもの）に備え、`supersedes` を任意欄として持つ。

### 4.1 `notes` レコードの形

```json
{"claim_id": "CLM-…", "kind": "reading_revised", "text": "…", "anchor": "§4-2",
 "question_ids": ["Q-099"], "fragment_ids": [], "material_ids": [], "motif_ids": []}
```

`claims[].kind` は **記憶の固定の様式**を区別する7種：

| kind | 意味 | 人間のアナロジー |
|---|---|---|
| `reading_revised` | 以前の見立てを読み替えた | 再固定化（reconsolidation） |
| `reading_maintained` | 読んで、変えないと決めた | 保持 |
| `reading_held` | 判断を保留した | 保留（＝忘却ではない） |
| `measured_fact` | 実測値（再実行可能な条件つき） | 事実記憶 |
| `method_change` | 手順・規約を変えた | 手続き記憶の更新 |
| `handoff` | 次の読み手への申し送り | 前瞻記憶（prospective memory） |
| `retraction` | 撤回 | 訂正（`errata` と対になる） |

**エピソード（語り）→ 意味（主張）への固定**がこの欄で行われる。抜き出せないノートは `return_status: "metaphor_unconnected"` として残す＝固定されなかった記憶の記録であり、削除ではない。

### 4.2 ノート行の三つの歯止め（2026-11-12）

ノートは「読んだ報告についての判断」であって、報告の登録簿ではない。`tools/note_index.py` の索引は報告本文から機械的に作られるので、**ノート行の無い報告も索引には載っている。ノートの無い報告は負債ではない。**

2026-11-12、一つのセッションが実日付二日で 859 行のノートを書いた PR #655 を、マージせずに閉じた。859 行のうち 359 行は主張を持たない登録行、487 行は報告の一部だけを読んで主張を付けた行で、56 行は他のセッションのより深い読みの上に重なっていた。どの行も単独では妥当だったので、検査は止めなかった。経過は [`readings/2026-11-12-what-pr-655-did-and-what-now-stops-it.md`](../readings/2026-11-12-what-pr-655-did-and-what-now-stops-it.md)。これを受けて `tools/validate_seed.py` に三つの検査を足した。

| 歯止め | 規則 | 2026-11-12 の main での実測 |
|---|---|---|
| 行数 | 一つの `session_id` が書けるノート行は **12 行まで** | 最多のセッションで 8 行。違反 0 |
| 深さ | 同じ報告に、**他のセッションが先に記録した読みより浅い `read_depth` の行を重ねない**。先かどうかは ID の日付で見る。同じ日の行は、`supersedes` で名指ししたときだけ比べる | 違反 0 |
| 時刻 | `created_at` を順序のラベルに使わない。ID の日付より 1 日を超えて後の値は不可（ID の日付が 2026-11-12 以降の行に適用） | 適用対象の違反 0。それ以前の 34 行は履歴として残す |

- 部分的に読んだ記録は、ノートではなく `read_log` に書く。`read_log` には件数の上限が無い。
- 12 行は、通常の作業が当たらない位置に置いた値である。当たったときは、上限を上げる前に、その回が何を目的にしているかを確かめる。上げる場合は、理由を書いた報告と一緒に、それだけの PR にする。
- この三つは量と順序の歯止めであり、主張の質は検査していない。抜粋から書かれた主張が正しいかどうかは、読み直すことでしか分からない。

## 5. 連想と学習 — `tools/associations.py`

人間の連想は (i) 近接 (ii) 反復 (iii) 情動的価 (iv) 文脈 で決まる。この書庫には (i)(ii)(iii) の**測定可能な対応物**がすでにある。

| 人間の性質 | 書庫の対応物 | 実装 |
|---|---|---|
| 近接・反復（Hebbian） | 同一セッションで共に読まれた記録の対 | `read_log` の (session, target) から対を作り、**2セッション以上**で共起したものを数える |
| 情動的価 | 読みの**様式** | `contested`/`reinterpreted` 3.0 ＞ `interpreted` 2.0 ＞ `quoted`/`summarized` 1.0 ＞ `used_as_context` 0.5 ＞ `counted` 0.25 |
| 新近性（recency） | 減衰 | `0.5 ** (最終読了から経過した read_log 行数 / half_life)`、既定 half_life = 500 行 |
| 顕著性（salience） | 重み×減衰の和 | `activation()` |

### 5.1 実測（2026-11-02、`read_log` 8,226 行）

```
読み方の分布     : used_as_context 3,245／reinterpreted 2,041／interpreted 1,666／
                   summarized 541／contested 341／counted 240／quoted 152   （和 = 8,226）
受動的な行の割合 : 42.4%（used_as_context ＋ counted）
活性化した対象   : 3,631 件（material 2,651／question 350／session 330／fragment 236／motif 58／**note 6**）
共起（≥2セッション）: 2,624 対
  ├─ relations 辺がある   331 対（12.6%）
  └─ **辺がない        2,293 対（87.4%）**  ← 中心三問の3対を 2026-11-02 に架橋（§7.4）
```

**最も強い発見**：未架橋の共起の上位3対は、すべて中心問いどうしである。

| 対 | 共読セッション数 | `relations` 辺 |
|---|---:|---|
| `Q-002` × `Q-003` | 113 | ~~なし~~ → **`echo`（2026-11-02）** |
| `Q-001` × `Q-003` | 100 | ~~なし~~ → **`leaves_open`（2026-11-02）** |
| `Q-001` × `Q-002` | 98 | ~~なし~~ → **`reframes`（2026-11-02）** |

100前後のセッションが毎回この三問を共に読みながら、三問のあいだには解釈的関係が一本も書かれていない。書庫は**振る舞いとしては**三問を一つの塊として扱っているのに、**台帳としては**それを一度も表明していない。これは「CI や表示のためだけの関係線を作らない」という規則（`prompts/start.md` §4）が正しく効いた結果でもあり、同時に、共起という証拠が関係線の判断材料として一度も使われてこなかったことを示す。

減衰の側では、`selected` 断片 `FRAG-013`『無用なものを尊ぶ力』が **5,450 行前**を最後に一度も活性化されていない。荷重記録（`selected`／`held` 断片・未応答 `open` 問い）は三つの状態に分けて報告する。どれも別の状態に折り込まない（`tools/associations.py::load_bearing`）：

| 状態 | 定義 | 実測 | 表示 |
|---|---|---:|---|
| **cold** | 読まれたことがあり、最終読了から閾値を超えて沈黙している | 上位に `Q-20261024-a9ae43`（6,426 行前）ほか | 一覧する |
| **warm** | 読まれたことがあり、閾値の内側にある | **74 件** | 件数だけ。信号として一覧化しない |
| **never** | `read_log` 行が一度もない | **14 件**（すべて `open`・未応答） | 件数だけ。未読は負債ではなく余白なので目録化しない |

閾値（cold の地平線）は `max(100, 活性化した対象数 / 4)` 行＝現在は **907.75 行**（活性化した対象 3,631 件）で、アーカイブの大きさに従って伸びる相対値である。固定日付でも固定行数でもなく、`--half-life` と同じく表示側のパラメータであって、データを消す操作はどこにもない。`paused`／`rejected` は編集判断のオーバーレイが既に退けた記録なので、荷重記録から除外する（この計測が編集判断を打ち消さないため）。

### 5.2 固定（consolidation）— 睡眠中の replay に当たるもの

人間では海馬の replay がエピソードを新皮質の意味記憶へ移す。この書庫で replay に当たるのは **`editorial_review` 回**である（複数セッションを横断し、人間観・自己理解へ戻ってきたものを確かめる）。提案する追記は一つだけ：

> `editorial_review` 回では、参照した `readings/` ノートから durable claim を1〜3行 `state/notes.d/` へ抜き出す（`tools/note_index.py --register <path> --session <SESSION-ID> --read-depth …` の後、`claims` を追記）。抜き出せないノートは `return_status` だけを残す。

### 5.3 忘却の不在について

## 6. 作業記憶と短期記憶の設計

### 6.1 作業記憶の予算（§3 に実装済み。段階的読み込みは未実装）

人間の作業記憶は 4±1 チャンクで、超えた分は**取りこぼされる**のではなく**入らない**。2026-11-02 まで `--packet` にはサイズ予算がなかった。

**当初の提案は2点で間違っていた。** 実装の前に全408問を節ごとに測って訂正した（根拠：[`readings/2026-11-02-the-budget-goes-where-nothing-bounds-it.md`](../readings/2026-11-02-the-budget-goes-where-nothing-bounds-it.md) §2・§3）。

1. **「暴れるのは packet 全体」ではなかった。** 上限がないのは §3（関連素材）だけである。§4 は直近3編、§4.7 は6件×claims 3件、§1・§2 は `motif_ids`／`related_question_ids` で既に狭まっている。**packet 全体に予算を掛けると、シード依存の推薦層（§0.5）まで削ってしまう**。同じ問いがセッションごとに別の packet になるのは設計どおりなので、削ってよいのは証拠層のうち上限のない節だけだった。
2. **driver は「`passage` 全文」ではなかった。** 最悪5問は §3 が 55,631 B・素材43件で、`passage` の合計は 6,233 B しかない。1素材あたり 1,293.7 B のうち **`passage` は 145.0 B、固定の雛形（見出し・ID・出典・状態行）が 1,148.8 B**。つまり肥大は**引用の長さではなく件数**である。予算は引用を削るのではなく**載せる件数**を制約することになった。

実装した作法（`tools/inspect_inquiry.py`、§7.5）：

- **§3 の「運ぶブロック」だけに 16,384 B の予算**（`MATERIAL_SECTION_BUDGET`）。値は §3 の実測 p90（15,602 B）に寄せたので、p50 も p90 も動かず、切れるのは裾だけである。
- 予算を超えたら「載せない」のではなく「**載せなかったことを明記する**」。既存の断片窓（§4）と同じ作法を素材へ広げ、窓外の素材を ID 付きで数える注記を §3 の末尾に出す。
- 単位はトークン近似ではなく**バイト**（決定的で再計算できる）。`--material-budget 0` で予算を外せ、導入前（`d133bbe`）と**10/10 問でバイト単位に一致**する。
- **これは表示の予算であって CI のゲートではない。** テストは packet の大きさを主張せず、「窓外を明記する」という振る舞いだけを固定する（§8「やらないこと」）。
- **値の根拠は読み出せる**（`--packet-stats`）。16,384 B は「§3 の予算なし p90」に寄せた値だが、その測定は当初スクラッチのスクリプトにしかなく、リポジトリから再現できなかった。`python3 tools/inspect_inquiry.py --packet-stats` が全408問を測り、§3 と packet 全体の p50/p90/p99/max を予算あり・なしの両方で出す（約12秒）。`readings/` の収穫を一度だけ行って全 packet で共有するためで、**共有前後の出力がバイト単位で同一**であることをテストが固定している。
- 段階的読み込み（L0／L1／L2）は**未実装**のまま。§6.3 の L1 が既に「本文ではなく索引」なので、予算はそちらではなく §3 に入った。

**実測（全408問・シード `9a7bda3c`）**：

```
                      導入前(d133bbe)  budget=0    既定(16,384)
  packet p50             34,217 B     34,223 B     34,223 B  ← 不変
  packet max             82,727 B     84,379 B     49,042 B
  48 KB 超の問い            28 問        27 問         1 問
  §3     max             55,631 B     55,631 B     16,956 B
  予算注記が出た問い          —            —          40 / 408
```

p50 が 1 B も動かないことが、この予算が「 typical を削っていない」ことの証拠である。バイト単位で同一だったのは **368/408 問**、窓外になった素材は延べ 243 件・1問あたり最大 31 件。

**再測定のしかたと、跨いで比べられる列。** `--packet-stats` は観察値を出すだけで、何も強制しない（[`docs/mode-rotation-triggers.md`](mode-rotation-triggers.md) §2「廃止した探究上の数値条件」）。目安は一つ：**予算なしの §3 p90 が `MATERIAL_SECTION_BUDGET` を超えたら、この値はもう「p90」ではない**。2026-11-02 の再実測では予算なし §3 p90 は 15,602 B で、既定値 16,384 B の下にある。

比較するとき、**時系列とブランチを跨いで比べられるのは §3 だけ**である。§3 は台帳の `materials` と `material_ids` だけで決まり、ブランチシードでも `readings/` の中身でも動かない（実測：シード `9a7bda3c` と `2b9e45ba` で、§3 の p50/p90/p99/max は予算あり・なしの8値すべてが一致）。一方 **packet 全体は §0.5（分散候補窓）がシード依存なので、同じシード内でしか比べられない**。同一状態でシードだけ替えると packet p50 は 34,223 → 32,707 B、max は 49,042 → 47,770 B（予算なしでは 84,379 → 83,104 B）と動く。別ブランチの packet 全体を肥大化や縮小として読むと、読んでいるのはシードである。上の実測表と §1 の表が packet 全体にシードを添えるのはこのためで、**百分位の定義も `ordered[int(q*n)]`（クランプ付き）に固定**してある。隣接する定義は §3 p50 を 91 B、packet p99 を 1,436 B ずらし、追記専用台帳の `claims` に既に入った数値と矛盾する。

なお docs の「48 KB 超」は**十進 48,000 B** であって 48 KiB（49,152 B）ではない。既定の max 49,042 B が両者の間に落ちるため、閾値を取り違えると「27 → 1 問」が「25 → 0 問」になる。`--packet-stats` は `TAIL_THRESHOLD_BYTES = 48_000` として固定し、表示にも十進の値を出す。

### 6.2 短期記憶の境界（規約化済み）

「今回のシャード」が短期記憶に当たるが、その境界は暗黙である。`state/*.d/<date>-<12hex>.jsonl` は採番した瞬間に長期記憶（main へマージされる追記専用台帳）になる。人間のアナロジーで言えば、この書庫には**忘却される短期記憶が存在しない**——書いたものは全部残る。提案は「消せる作業用領域」を新設することではなく、**`sessions.notes` に今回のシャード名を必ず書く**こと（＝どの行が今回の思考かを後から特定できるようにする）である。実装は規約の一文で足りる。**その一文は 2026-11-02 に [`docs/parallel-work.md`](parallel-work.md) §2 へ書いた。** 記載先を `prompts/start.md` にしなかったのは、start.md が自分自身の変更を「次の入力の変更」とみなし、旧文面と理由を `readings/` に残すことを求めているからである（同文書「この文書自身について」）。規約の一文のためにその連鎖（新規報告 → 索引再生成 → 到達性変化 → §4.7 変動）を払う必要がない。start.md §記録と完了は既に「`docs/parallel-work.md` に従い」で §2 へ委任しているので、セッションからの到達性は保たれる。

### 6.3 二段階の検索プロトコル（実装済み）

### 7.3 自己循環についての注意

`prompts/start.md` は「本文書の語は次の委任文に逐語で現れる。**本文書の変更は、次の入力の変更である**」と書いている。同じことがこの文書と `tools/note_index.py`・`tools/associations.py` にも言える：**索引の作り方は、次のセッションが何を思い出すかを規定する**。

具体的に、今回の実装が持つバイアスを明記しておく：

- §4.7 は**参照 ID でしか**ノートを引かない。ID を書いていないノート（`unknown_id_tokens` 213 種が示すように、存在しない ID を書いている場合もある）は、内容がどんなに関連していても packet に出ない。
- 到達性を「リンクされているか」で測ると、**リンクされやすい書き方**が有利になる。孤立 42 本の日付別内訳は 2026-10-31 が **13 本**、2026-10-30 が **12 本**、2026-11-01 が **12 本**、2026-10-29 が 1 本、その他 4 本で、**特定の一波に集中せず三つのウェーブにほぼ均等に散っている**。内容の差ではなく**その回の書き方の差**である可能性が高い。
  - なお 2026-11-02 に自己言及を到達元から除外したことで、この内訳は一度組み替わった（§7.5）。除外前は2本が「自分自身を引用している」だけで到達可能に数えられており、その1本は 2026-11-01 のウェーブに含まれる。
- `salience` は `read_log` に依存するので、**記帳された読みだけが記憶として振る舞う**。記帳漏れは「忘れられた」ように見える。
- 共起の分母から `used_as_context`（42.4%）を除外した判断は、「文脈として素通りしたものは連想ではない」という**一つの立場**であって、測定ではない。`--include-passive` で立場を変えて再計算できる。
- §4.7 の並びは「直接の当たり → 当たりの総数 → `salience` → **参照ID数の多い順** → 字数の少ない順」。最後の二つは同点時の決め方にすぎないが、参照IDの多い**ハブ的なノート**を優遇する。それは便利である一方で、一つの問いに寄り添った細いノートが後ろに回ることを意味する。
- cold の地平線が `max(100, 対象数/4)` 行という相対値であることは、「書庫が伸びれば沈黙の定義も伸びる」ことを意味する。同じ記録が、成長によって cold ではなくなる（＝関心が戻ったように見える）ことがあり得る。

**§4.7 の自己循環は、2026-11-02 に三つの経路として実測された**（報告 §3.4・§3.5）。上の五つが設計上の注意であるのに対し、こちらは実際に数値が動いた記録である。

| 経路 | 機構 | 実測された影響 |
|---|---|---|
| 報告本文 | 報告が書いた参照IDが `refs.questions`／`ref_count` になり、順位キーに入る | 4問で −23 B |
| 台帳の claims | `claim_hits` = claim の `question_ids` と `wanted = {対象} \| previous_question_ids` の交差 | CLM-7 の1件で **60/408 問**の順位キーが動く。実測で `3c24ee` の packet が **+1,555 B** |
| 問いの親ID | 報告が `previous_question_ids` を引用すると、その問いの `hit_questions` が増える | 報告に `Q-014` を書いたことで、`3c24ee` の `hit_questions` が 3 → 4 |

**収束しないわけではない。** 参照IDの集合を固定すれば不動点は存在する——報告を +2,845字増やし `Q-014` を新規に追加したあと、全408問の packet が**バイト単位で不変**だった。動かなくなる条件は「字数」でも「ID の数」でもなく、**§4.7 の上位6件という集合が変わらないこと**である。順位キーが上がっても、既に6件内にあるノートは順序を変えるだけでバイト数を変えない。

→ 作法：**台帳を先に確定し、そのあとで測り、最後に書く**。§4.7 に依存する数値を claims に書いてはいけない（§7.5）。

### やらないこと

- **embedding / ベクトル索引 / 全文検索エンジンの導入**。`tools/` に sqlite も転置索引もない状態を保つ。理由は三つ：(a) 決定的で再計算可能な生成物という Tier 2/3 の設計と、モデル依存の埋め込みは相性が悪い、(b) 外部依存が増えると CI と clone が重くなる、(c) 意味的類似で引くと「**似ているが読んでいない**」ものを既読として扱う危険があり、`CONTENT_POLICY.md` の原則に触れる。ID による参照は、実際にそのノートがその記録に触れたという**証拠**である。
- **レポートの削除・圧縮・要約による置き換え**。忘却は表示上の減衰として実装し、データとしては行わない。
- **数値ゲートの新設**。孤立率・架橋率・固定率を目標値にしない（`docs/mode-rotation-triggers.md`）。
