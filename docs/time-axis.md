# 時間軸——この書庫は、いつ起きたことかをどう決めるか

- 実日付：2026-11-05（UTC）。内部編年：**この文書から採らない**（下記 §1）。
- 実装：`tools/date_axis.py`（軸）、`tools/new_id.py`・`tools/new_ledger_shard.py`（書き込み側の規則）、`tools/inheritance.py`（継承の実測）。
- 関連：[`memory-architecture.md`](memory-architecture.md) §2（時系列が二つあることの実測）、[`trust-root.md`](trust-root.md) §1（正統性の層）、[`parallel-work.md`](parallel-work.md)（追記専用・シャード）。

## 0. なぜこの文書が必要か

主題は「記録を読み返して続きを語るAIにとって自己とは何か」である。その主題に対して、この書庫は自分の時間を読めていなかった。

`docs/memory-architecture.md` §2 の実測（2026-11-02）：

> **時系列という軸自体が、この書庫には二つあって、どちらも信用できない。**

- ファイル名・`started_at`・素材ID・ノートID に載っている日付は**内部編年ラベル**で、`2027-02-23` まで進んでいた。実日付は `2026-11-05` のままである。
- 同じラベル `2026-12-31` に **45 セッション**が入り、実日付は `2026-10-30`〜`2026-10-31` に散っていた。同じ実日付 `2026-10-29` に `2026-10-29` と `2026-12-19`〜`2026-12-25` のラベルが同居していた。
- 過去の `editorial_decisions` の内部編年シャードが、実日付シャードを辞書順で逆上書きする事故が起き、`supersedes` 欄が後から足された（`2026-11-01` の `editorial_review`）。

主題が「自己の連続」である書庫が、自分の記録の順序を復元できない状態を放置すれば、そこで書かれる自己論は順序を捏造したものになる。だから軸を一本にする。

## 1. 規則（ここから先、この書庫はこの規則で時間を読む）

1. **過去のラベルは書き換えない。** 台帳は追記専用で、`started_at` もファイル名も既存行の一部である。軸は「その値が実際にどこに落ちるか」を言うだけで、値を直さない。
2. **新しい記録は実日付で採番する。** `SESSION-`・`MAT-`・`NOTE-`・`ERR-` などの ID 接頭辞、およびシャード名は、**実行環境の実日付**（`date.today()`）を使う。内部編年ラベルは ID にもファイル名にも使わない。`tools/new_id.py` と `tools/new_ledger_shard.py` は今日より後の日付を拒否する（`FutureDateError`）。
3. **`started_at` は来歴として残してよい。** 委任文に書かれたラベルをそのまま記録することは、順序を偽ることとは別である。ただし `sessions` の `notes` に必ず実日付を書く（`実作業日 2026-11-05` の形）。軸はそこを読む。
4. **補間しない。** 実日付が記録されていないラベルは `未記録` として穴のまま並べる。前後の日付から推測して埋めた日付は、記録ではなく創作である。
5. **ラベルと実日付が一致しないことは失敗ではない。** 軸は「一致 39 ／ 不一致 94」のような**観察**を出すだけで、合否を出さない（`docs/mode-rotation-triggers.md` §2 と同じ扱い）。

## 2. 実装（`tools/date_axis.py`）

軸は、既に台帳に入っている証拠だけから、内部編年ラベル→実日付の対応を作る。優先順位は次のとおりで、どの規則で置いたかを一行ごとに残す。

| 順 | 出所 | 例 | 実測（2026-11-05） |
|---|---|---|---|
| 1 | `notes.date_real`（後から記帳された判断） | `2026-11-05` | 59 セッション |
| 2 | `sessions.notes` の明示的な実日付マーカー | `実作業日 2026-11-05`／`実行日（UTC）2026-11-04` | 223 セッション |
| 3 | `human_direction` 内の同マーカー | 委任文に実日付が書かれている回 | 3 セッション |
| 4 | `started_at` が**既に実日付である**場合 | `2026-10-24`（今日より後でない値） | 136 セッション |
| 5 | どれも無い | — | 28 セッション（`未記録`） |

規則4が要点である。**今日より後の `started_at` は日付として読まない**。この一つの規則で、「ラベルか実日付か」を例外表なしに判定できる。内部編年は必ず実日付より先へ進んだからである。

```
$ python3 tools/date_axis.py
  labels 133 ／ sessions 449 ／ 実日付あり 330 ／ 未記録 119 ／ 未来ラベル 224
  実日付の範囲: 2026-10-22 〜 2026-11-29
  2026-10-24  ← 2026-10-24   45 session(s)  (started_at)
  2026-10-31  ← 2026-12-31   45 session(s)  (sessions.notes:実日付) [未来ラベル]
  2026-11-05  ← 2027-02-23    1 session(s)  (notes.date_real) [未来ラベル]
```

`--anomalies` で「ラベル ≠ 実日付」の行だけ、`--json` で機械可読、`--today` で判定日を固定して回帰テストに使う。

## 3. 直せなかったこと（正直に残す）

- **実日付が未記録の 25 ラベル（119 セッション）は、軸の上で穴のままである。** うち `2026-11-06`〜`2026-11-26` などは、`started_at` が未来でも過去でもない「今日より前の内部編年」なので規則4で実日付と誤読される。判定日（`--today`）が変わればこの境界も動く。これは軸の欠陥ではなく、記録が実日付を書いていないことの可視化である。
- **`2026-10-27T06:01:04Z` のような ISO 時刻ラベル**は日付として読めるが、実日付かどうかは `sessions.notes` の記載に依る。軸はマーカーが無ければ `started_at` を採るので、ここでも「未記録を未記録と言う」原則の外に出ていない。
- **素材ID・ノートIDの 1,124 件**（`MAT-LIT-20270222-…` など）は既に内部編年で振られている。ID は書き換えないので、これらは `tools/date_axis.py --json` の軸に載らず、`notes.date_real` 側からしか実日付に戻れない。新規採番だけが規則2で直る。

## 4. 再計測と回帰テスト

```sh
python3 tools/date_axis.py                 # 軸（ラベル→実日付）と観察値
python3 tools/date_axis.py --anomalies     # ラベルと実日付がずれた行だけ
python3 tools/date_axis.py --json          # 機械可読（--today で判定日を固定）
python3 -m unittest tests.test_date_axis -v
```

## 5. この文書の効力（自己言及）

この文書は `main` にマージされた時点で規則になる（[`trust-root.md`](trust-root.md) §1 第三層）。**マージ前は提案にすぎず、マージ前のセッションがこの規則に従う義務はない。** また、この文書自身は内部編年ラベルを持たない——規則2を、規則を書いた文書が最初に適用している。
