# ビューアのスナップショット模型——8.4秒の再構築を、リクエストの外へ出す

- **実作業日**：2026-11-14（UTC）
- **起点**：`cda8292e790040f30552a7537674e0f6f67cf0b3`（`main`）
- **対象**：`tools/serve_viewer.py`、`viewer/app.js`、`tests/test_server.py`
- **台帳行の追加・変更**：なし（素材・断片・問い・関係・セッション・ノート・評価・`read_log` いずれも0行）。`state/` は触っていない。

---

## §1 症状

全601テストのうち `tests/test_server.py` の3件が、このサンドボックスでだけ落ちた。

- `test_api_state_index_and_404`（HTTP クライアントの `TimeoutError`）
- `test_api_reports_isolation_and_exclamation_instead_of_rejecting_them`（同上）
- `test_concurrent_reads_during_atomic_rewrites`（6スレッドの読み手が全滅）

`origin/main` の素のチェックアウトでも同じ3件が落ちたので、この差分が原因ではない。では何が原因か。

## §2 診断

`/api/state` の1回の再構築を分解して測った（このサンドボックス、素材4,272件・報告779本）。

| 段階 | 時間 |
|---|---:|
| 台帳の読み込み（union＋安定読み） | 0.55 s |
| 派生パネル17種（`voice_audit` と16の監査鏡） | **6.36 s** |
| うち最重の `vegetal_audit` | 1.10 s |
| `json.dumps`（21.4 MB） | 0.17 s |
| 合計（コールド） | **7.3〜8.4 s** |
| 合計（ウォーム） | 0.03 s |

派生パネルは断片247・素材4,272・報告779の全文を、17種それぞれが独立に走査する。`_aggregate_docs` が1監査あたり4回、`scan_text` が5,545文書、`re.Pattern.search` が全体で450万回。**1リクエストあたり8秒**である。

ここから3つの設計上の帰結が出ていた。

1. 依頼が来るたびに8秒かかる。読み手の期限が10秒なら、遅い機械では正しいデータを返しながら期限を超える。
2. 台帳が書き換わるたびにキャッシュ鍵が変わる。並行書き換えテストでは、6スレッドが8秒の再構築に**直列に並ぶ**。実際に測ると、6リクエストがすべて8.4秒で返り、次のリクエストはさらに待つ。
3. 結果として、テストは「壊れている」と報告するが、サーバーは壊れていない。**遅さを正しさの信号として読んでいた**のはテストの側である。

## §3 変更

サーバーに**スナップショット**の語を入れた。リクエストは最新スナップショットを即座に返し、再構築は背景で1本だけ走る。

- `read_archive_payload(fresh=False)`
  - ディスク上のファイル指紋（`state/` と `readings/` の inode・サイズ・mtime、1,514項目、13 ms）がスナップショットと一致 → そのまま返す（`X-Archive-Snapshot: fresh`）。
  - 一致しない → **前のスナップショットをそのまま返し**、背景スレッドを1本だけ起動する（`stale`、`X-Archive-Snapshot-Age-Ms` に経過ミリ秒）。
  - `fresh=True`（`/api/state?fresh=1`）→ 再構築を待って新しいスナップショットを返す。
  - スナップショットが無い最初の1回だけ、リクエストスレッドで構築する。
- スナップショットは `(root, 指紋, payload, 直列化済みバイト列, 構築時刻)`。`root` を鍵に含めたのは、テストが `ROOT` を一時ディレクトリへ差し替えるためで、**別リポジトリ用のスナップショットを配らない**ようにするため。
- 再構築中にファイルが変わっていたら `fresh` とは名乗らず `stale` と返し、もう一度だけ背景再構築を起こす。**自分の出力が現在のファイルと一致しないときに「最新」と言わない**。
- `main()` は起動時に背景で最初のスナップショットを作る（`archive-warm-up`）。最初のページ表示が8秒待たないため。テストは `start_server()` を使うので、この経路を通らない（＝リクエスト経路の検証はそのまま）。
- `viewer/app.js` は `X-Archive-Snapshot: stale` を見たときだけ、統計帯に「スナップショット更新中」の小さな徽章を足す。再描画はしない（読んでいる位置を動かさないため）。

## §4 変更後の実測（同じサンドボックス）

| 条件 | 変更前 | 変更後 |
|---|---:|---:|
| コールドの1回目 | 7.6 s | 7.6 s（変わらない。ここは削っていない） |
| 書き換え中の6スレッド | 6リクエストすべて 8.4 s、期限超過で失敗 | 46リクエスト、中央値 **281 ms**、最大 **467 ms**、失敗0 |
| 書き換え直後の1回 | 8.4 s | **70 ms**（前スナップショット、`Age-Ms: 2470`） |
| `?fresh=1`（書き換え後） | —（存在しない） | 0.67 s（背景再構築の結果を待つ） |

23 MB の転送そのものが中央値の大半を占める。**再構築の8秒は消えていない。リクエストの外へ出ただけ**である。

## §5 テストの変更

- 3件の失敗は「10秒という固定の期限」と「8秒の処理」の差で起きていた。期限は環境変数 `ARCHIVE_TEST_TIMEOUT`（既定120秒）で変えられる**生存期限**にし、遅さを合否にしない。
- 代わりに、新しい保証を直接試験する `test_stale_snapshot_is_served_while_a_refresh_runs` を足した。1.5秒かかる再構築を注入し、(1) 台帳を1行追記する、(2) 次のリクエストが1秒以内に200で返り、`stale` と名乗り、行数は追記前のまま、(3) `?fresh=1` が追記後の行数を返す、を確かめる。**遅さではなく、約束を測る。**
- 既存の7件は意味を変えずに通した（ウォーム時に `json.dumps` を呼ばないこと、4スレッドで再構築が1回であること、読み取り不能時に500のJSONを返すこと、`_read_archive_payload_once` が同期的に最新を返すこと）。

## §6 やっていないこと

- 派生パネルの計算量は減らしていない。17種×5,545文書の走査はそのまま8秒かかる。**キャッシュの粒度を監査ごとに分ける**、**1パスで複数の語彙を数える**、**再構築をプロセス並列にする**のいずれも試していない。
- コールドスタートは7.6秒のまま。起動時のウォームは、その8秒を「ブラウザが開く前」へ移すだけで、なくしてはいない。
- スナップショットの古さの上限は「再構築1回ぶん」。書き込みが続く間は古いままでありうる。`?fresh=1` を知らない消費者は、遅れたページを見る。
- `data.json`（静的な書き出し）はこの経路を通らない。
